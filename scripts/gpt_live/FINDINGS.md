# GPT-Live 실험 기록

GPT-Live 도입 실험과 레이 적용 후의 실측 기록. 설계 선택 이유는
[decisions-wip.md](../../docs/decisions-wip.md), 실행·로그 확인법은
[브리지 문서](../../docs/modules/bridge.md#live-실행과-싱크-진단)에 둔다.
실험 도구는 `mic_live.py`(마이크 또는 TTS 스크립트 입력 → GPT-Live → 스피커, 전 이벤트 로그).
실행 로그는 `logs/`, 공식 문서 원문은 `ref/`, 재현용 스크립트는 `script_*.txt`.

기록 기간: 2026-09-14 ~ 2026-10-07. 초기 실험 환경: Raspberry Pi 5, Wi-Fi(5 GHz), reSpeaker XVF3800(마이크·스피커, 온칩 AEC), 모델 `gpt-live-1`, 백엔드 `gpt-5.4-mini`.

이후 유선 비교·로봇 실기 실험은 각 항목에 날짜와 조건을 적었다. API 사양·요금·한도는 당시 문서와 관측 기준이며, 현재 보증값을 뜻하지 않는다.

---

## 1. API 기본 사실 (문서 + 확인)

- 엔드포인트 `wss://api.openai.com/v1/live/sessions`. Realtime API와 별개. 클라이언트 이벤트 11종, 서버 이벤트 21종 (`ref/api-reference-live-primary-websocket.md`).
- **수동 턴 제어 이벤트가 없다.** 턴 시작/끝, 발화 시작/끝, 응답 생성/취소 같은 이벤트가 존재하지 않는다. 모델이 언제 말하고 멈출지를 전부 결정한다.
- 세션 시작 시 고정되는 것: 모델, `instructions`(≤16,384 토큰), 오디오 포맷, 목소리, 위임 모드. 이후에는 append(≤500 토큰)로 추가만 가능.
- 오디오: WebSocket은 raw PCM16 mono, 16 kHz 또는 24 kHz(입·출력 공유). 단독 실험 도구는 16 kHz 사용(reSpeaker 캡처와 동일). 레이 엔진은 `BRIDGE_SAMPLE_RATE`에 맞춰 24 kHz 사용.
- 세션 만료: `session.started`의 `expires_at`로 계산하면 **120분**. 문서에는 수치 없음.
- 컨텍스트 128k 토큰(instructions + 대화 텍스트 + 오디오 토큰). `session.usage.updated`(15초 간격)의 `context_window.usage_ratio`로 사용량 확인 가능. 90% 초과 시 원본 instructions + 최근 8,192 토큰 요약을 들고 엔진 교체(문서).
- **채워지는 속도(실측, 3분)**: 모델이 말하는 중 약 48 tok/s, 무음(마이크만 흐름) 약 20 tok/s. → 90% 도달까지 계속 말하면 약 40분, 보통 대화 약 50분, 거의 무음 약 95분. 2시간 세션이면 교체 2회 정도. 교체 자체는 미관찰.
- openai-python 3.13.0에 `client.live.connect()`와 전체 타입 포함. 도입 전 프로젝트는 `openai<2.0`이었으며, 현재 의존성은 `openai[realtime]>=3.13,<4.0`으로 업그레이드되어 있다.
- 요금 $0.05/분(무음 포함, 초 단위). 동시 세션 수 제한(Tier1 25).

## 2. 오디오 출력 특성

- **실시간 페이싱.** 100 ms(16 kHz에서 3200 B) 조각이 초당 약 10개 온다. TTS처럼 앞서 보내지 않는다. 말하지 않을 때도 무음 조각이 같은 속도로 계속 온다(전화선과 같음). 조각 크기·속도는 **관측치**로 문서 보증이 없다(WebSocket 가이드: "Output audio events have no timing fields"). 입력은 문서가 실시간을 요구한다("paced at its recorded sample rate").
- **총량은 실시간보다 적다 — 유실 (2026-09-16 확정).** `store: true` 세션의 서버 녹음(오른쪽 채널 = 출력)과 받은 오디오를 상호상관으로 대조: 받은 오디오는 생성분과 샘플 단위로 일치하고(오프셋 −2 ms 고정, 상관 1.00) 빠진 구간만 녹음에 남는다(지연 아님). 유선·전부 무음 3분 97.3%(단일 프레임 누락 ~36회, 도착 간격 200 ms), 유선·90% 말소리 3분 99.8%(400 ms 한 번, 도착 간격 흔적 없음), Wi-Fi 7세션 96~98.5%. 유실은 무음에 집중되고, 말소리 유실은 드물지만 감지·복구 불가. 서버 제어 가이드 "Reflected output ranges can have gaps for dropped frames". 사이드밴드 타임스탬프 검증은 WS 프라이머리 세션에 attach 불가(404, WebRTC·SIP 전용)라 못 쓴다.
- 따라서 클라이언트에 지터 버퍼가 필수이고, 그 크기가 곧 추가 지연이다. 한 번 밀린 지연은 서버가 따라잡아 주지 않으므로 무음 조각을 버리는 등으로 스스로 줄여야 한다.
- 조각 간격 분포(Wi-Fi, 5분, 2,910개): 95%가 110 ms 이내, 200 ms 초과 31회(약 10초에 1회), 300~400 ms 17회, 최대 510 ms. 이후 여러 실행에서도 최대 500 ms 안팎. **400 ms 여유면 5분에 1회 끊김, 500 ms 넘게 잡아야 전부 흡수.** **유선(2026-09-16, 3분×3)**: 97.9%가 110 ms 이내, 최대 214~363 ms, 250 ms 초과 0~2회 — 정지는 Wi-Fi 구간이 원인.
- 단독 실험에서 지연은 발화·무음에 차이 없었고(전송량이 같음), Wi-Fi 절전 끄기는 효과 없었다.
  09-16 로봇 세션에서는 wlan0 링크가 −61 dBm, 19.5 Mbit/s였고 정지 뒤 몰림에도 정지 창 도착률은
  90~94%로 총량이 회복되지 않았다. 로봇에서 발화·무음별 정지 빈도는 별도 집계하지 않았다.
- 레이 C++ 재생부는 큐가 비면 자체 무음을 삽입한다. 초기에는 분석의 두 사이클 선행을 재생 큐의 720 ms 여유로 보았으나, 실측상 실효 여유는 약 360 ms였다. 이 차이가 소리–입 싱크 누적의 원인이었고, 공유 지점의 채우기·되돌리기로 방어했다(§2.1).
- `stream_start`가 재생 중 들어오면 수신 스레드가 즉시 버퍼를 비우고 플래그를 바꾸므로(stale 청크 방어), 발화를 겹쳐 보내면 상태가 뒤엉킨다. 기존 SessionLoop는 `playback_complete` 전에 다음 `stream_start`를 보내지 않아 문제 없음. 도입 당시 "세션 = 스트림 하나"로 결정(2026-09-15). 현재는 `live=true`로 무음을 포함한 연속 스트림을 유지하되, 노래 재생 때는 스트림을 닫고 재생 완료 뒤 다시 연다.
- 첫 소리까지: `session.started`까지 1.5~3.5초. **모델은 스스로 인사하지 않는다** — 재촉 없이 아무도 말하지 않으면 180초 내내 무음(2026-09-16 run1). 초기 실험에서 "스스로 인사"로 보였던 것은 열린 마이크의 방 소리·사용자 말에 반응한 것. `session.commentary.append("Begin now …")`로 재촉하면 0.9초 만에 인사(run2). 세션 시작 직후 첫 0.2초에 진폭 ≤50의 미세 비영 샘플이 오므로 "말소리" 판정은 rms 기준이어야 한다.

### 2.1 레이 오디오·모션 싱크 — 원인과 방어 실험 (2026-09-16 기록)

아래 수치는 당시 실기 기록이다. 파이썬 무음 보정과 C++ 프리버퍼·공유 덩이 채우기·되돌리기는
2026-10-02 코드에도 적용되어 있다. 이후 물리 오프셋·DAC 드리프트 측정은
[설계 기록의 싱크 실측 절](../../docs/decisions-wip.md#gpt-live-오디오모션-싱크-실측--가짜-live-클라이언트로-물리-오프셋드리프트-측정)을 참고한다.

- **시작 시 여유 부족**: 첫 360 ms 덩이가 차자마자 모션 시계를 시작하면 매 사이클 데이터가 막 도착해
  모터 틱이 4 ms 간격으로 몰아쳤다(16:30 로그). 두 덩이(720 ms)를 모은 뒤 시작하자 초반 끊김이 사라졌다.
  초기 비교 실험에서는 멈춤 중앙값 359 ms·90% 527 ms였고, 여유 한 덩이는 멈춤의 절반이 남았다.
  두 덩이는 84초에 7회, 세 덩이는 3회로 줄었지만 서버 총량 부족과 네트워크 정지는 별도 보정이 필요했다.
- **서버 총량 부족**: 출력이 2~3% 짧으면 720 ms 여유가 약 20초에 소진되어 무음 중에도 회복되지 않았다.
  파이썬에서 lead = 보낸 오디오 길이 − 첫 전송 이후 경과 시간으로 추적했다. 정확히 0인 조각 뒤
  lead < −0.1 s면 0까지 채우고, lead > +0.3 s면 무음 조각을 버렸다. 긴 발화에서는 어절 사이 쉼
  (rms < 30), lead < −0.3 s일 때 한 조각만 채웠다. 107/68/181초 세션에서 lead가 ±0.15 s 안에
  머물고 멈춤은 네트워크 정지 시점 1~2회로 줄었다. 말소리 조각은 버리지 않는다.
- **재생기만 무음을 넣으면 싱크가 누적**: 17:56, 181초 세션의 오차는 0 → 306 ms → 711 ms로
  증가했고 재생기 무음 누계 300 ms → 700 ms와 일치했다. 조각 간격 390/1,110 ms 정지 뒤 소리만
  밀리고 모션은 절대 시계로 따라잡았다. 실효 여유가 약 360 ms인 이유는 `stream_and_split`이
  360 ms씩만 재생 큐에 넘겨 나머지가 원시 버퍼에 남기 때문이었다.
- **공유 지점 채우기**: `stream_and_split`에서 사이클 기한 + 450 ms까지 기다린 뒤 부족분을 0으로
  채워 재생·분석 큐에 같은 덩이를 넘겼다. 시작 전과 스트림 종료 뒤 꼬리는 채우지 않는다.
  13:05, Wi-Fi 166초 시험에서 23~33초 사이 20~60 ms씩 9회, 총 240 ms를 채운 뒤 나머지
  130초는 채움 0회. 재생기 무음 0 ms, lag 최대 14 ms, 틱 간격 최대 44 ms였다.
  싱크는 유지됐지만 말소리의 미세 구멍과 추가 지연 240 ms가 남았다.
- **시작 여유 S + 무음 되돌리기**: 두 덩이 외에 S만큼 원시 버퍼를 남기고 시작했다.
  S=200, 13:41 Wi-Fi 368초 시험: 540 ms 정지에서 540 ms를 채우고 이후 무음에서 320 ms를
  되돌렸다. 나머지는 유실분이라 되돌릴 잉여가 없었고 버퍼는 S 수준으로 복귀했다.
  lag 0~11 ms, 재생기 무음·틱 끊김 0회. 조각 간격 330~360 ms 네 번은 채움 없이 흡수했다.
  82초의 60 ms 채움은 파이썬 보정 밴드가 여유를 100 ms 깎은 상태에서 240 ms 지터가 겹친 경우였다.
- **S=400 선택 근거**: 당시 Wi-Fi 25.8분 분포에서 간격 >300 ms는 분당 1회, >400은 2.9분당,
  >450은 5.2분당, >500은 8.6분당 1회, 최대 1,110 ms였다. S=400을 채택했으며
  정상 상태 오프셋은 720+400=1,120 ms다. 당시 예측은 채움 5~9분당 1회였으나 긴 발화에서는
  파이썬 보정 문턱 때문에 흡수 여유가 줄어든다. 유선(최대 214~363 ms)은 S=100~200 후보였다.
  이는 해당 실험 조건의 판단이며 이후 더 긴 정지도 관측됐다(설계 기록의 09-17 실측).
- **되돌리기 조건과 비용**: C++가 채운 누계가 있고 원시 버퍼가 200 ms보다 많이 남았으면,
  앞쪽 0 샘플을 잉여량과 채운 누계 중 작은 만큼 버린다. 말소리에는 손대지 않지만 자연스러운
  문장 사이 쉼이 수백 ms 짧아질 수 있다. 재생기 자체 무음은 마지막 폴백으로 남는다.
- **유선에서도 파이썬 보정 필요**: 무음 유실 1~3%는 720 ms 여유를 27~72초에 소진시킨다.
  정지 중에는 조각이 없어 파이썬 보정이 발동하지 않으므로, 정지 방어는 C++가 맡는다.
  Wi-Fi 17:56 세션은 3분에 약 5초를 채웠고, 유선에서는 100 ms 단위의 작고 잦은 보정이었다.

### 2.2 호출어 이후 청취 지연과 장치 점유 (2026-09-16 기록)

- 호출어 감지 → 마이크 전송 시작은 4.6~6.2초였다. 인사 WAV 2.07초와 연결 2.0~4.1초가 직렬이었다.
  인사 재생과 연결을 겹치고 연결 즉시 마이크를 보내도록 구현했다. 인사의 `playback_complete` 뒤
  라이브 스트림을 열며, 그 전 모델 출력은 버린다(10초 폴백). 예상 청취 시작은 2.0~4.1초였으며
  이 개선치의 실기 검증 결과는 기존 기록에 없다.
- LED의 IDLE은 연결 후 마이크 전송 시작, SLEEPING은 종료 시 입력 mute 시점에 맞췄다.
  인사 재생 중 먼저 켜지던 표시를 제거한 구현은 현재 코드에도 있다. 실기 검증 항목은 §7에 남겼다.
- 감지 이전에는 VAD 후행 300 ms + Google STT 왕복 0.5~1초가 있었다. 감지 → 인사 재생은 로그상 즉시였다.
- GNOME 소리 설정을 열어 두면 PipeWire가 마이크를 점유해 `No input device matching 'respeaker'`가 발생했다.
  웨이크워드 자체의 인식 문제로 오인했던 사례다.

## 3. 전사 (transcript)

- `session.input_transcript.delta` / `session.output_transcript.delta`가 200 ms 오디오 단위로 온다. 턴 완료 이벤트 없음, 조각이 글자 중간에서 끊김, 사용자·모델 조각이 인터리브. 턴 묶기는 클라이언트 몫(SDK `TranscriptGrouper` 참고).
- `start_ms/end_ms`는 세션 타임라인상 **소리가 있었던 구간**이고, 전사가 도착하는 시각은 그보다 0.6~0.8초 늦다.
- 전사가 별도 인식기인지 모델 자체 출력인지 **문서·레퍼런스 어디에도 없음.** 관측: (a) 사용자 말을 잘못 들었을 때 전사와 모델 반응이 두 번 연속 같은 방식으로 틀림("날짜가" → "날 차로 친"), (b) 출력 전사에서 같은 한국어 숫자 발화가 "1. 2. 3." / "일, 이, 삼" / "하나, 둘, 셋"으로 실행마다 다르게 표기됨. → 전사는 모델의 이해/생성 텍스트로 보는 것이 자연스럽다. **모델의 오인식을 전사로 검출할 수 없다.**
- 문서 경고: "transcripts can contain mistakes, unfinished phrases, and later corrections". 정정이 어떤 형태로 오는지는 미확인.

## 4. 위임 (delegation)

- 위임 여부는 **지시 없이도 모델이 스스로 판단**한다(기본 instructions만으로 날씨 질문을 위임). 위임 정책 지시문은 "무엇을 넘기고 무엇을 직접 답할지"의 경계를 좁히는 용도.
- 모드는 세션당 하나(`client` | `responses`). 변경은 새 세션.

### client 모드
- `session.delegation.created`에는 `id`, `target`, `offset_ms`만 있고 **요청 텍스트가 없다**(API 설계). 우리가 전사에서 요청을 재구성해야 한다.
- 결과는 `session.commentary.append(delegation_id=…)`로 돌려주면 모델이 패러프레이즈해 말한다(고정 답 "서울은 맑고 24도야" → "서울은 지금 맑고 24도야. 가볍게 나가도 괜찮을 듯!").
- 답을 안 주면 모델은 "잠깐만 기다려줘", "아직 로딩 중이야"를 반복하며 무한 대기하고, 재촉하면 위임을 다시 생성한다.
- 결과가 너무 빨리(1.8초) 오면 "확인해볼게" 직후 결과를 말해 어색해진다.

### responses 모드
- OpenAI가 백엔드 모델을 호출한다. 백엔드 설정(`delegation.responses`: model, instructions, tools, reasoning 등)은 `session.update`로 세션 중 변경 가능한 유일한 영역.
- 백엔드 스트리밍 이벤트가 `response.event` 봉투로 그대로 중계된다(`response.created`, `output_text.delta`, `web_search_call.*`, `output_item.done`, `completed`). 라이프사이클 스냅샷은 input/tools/output이 비워져 온다.
- **백엔드가 받는 입력은 대화 이력 전체**(user/assistant 메시지, 전사 텍스트 그대로, 모델의 직전 발화 포함). 시드 히스토리 5개 전부, 음성 대화 3턴 전부, 60초 침묵 뒤에도 앞 턴 참조 가능. (백엔드에 "받은 입력을 인용하라"는 지시로 확인. 단 백엔드가 이 지시를 매번 따르지는 않아 "이것만 받았다"의 증거로는 못 쓴다.)
- **백엔드 입력의 실제 구조 (2026-10-02, 프로브 백엔드로 인용시켜 확인)**: ① system "Knowledge cutoff …" ② developer
  OpenAI 상용구(사용자 추정 위치·오늘 날짜·툴 이름 목록) ③ developer "You are a backend model supporting a realtime frontend
  assistant … **Shared session instructions**: *대화 모델의 세션 instructions 전문* … `<backend_delegation_instructions>`:
  *우리 `delegation.responses.instructions`*" ④ user 메시지 **하나**에 SRT 형식으로 포장된 전사("The conversation below is an
  SRT-style transcript … [User speech transcript] …"). 즉 **백엔드는 라이브 지시문을 통째로 같이 받는다**(YES-RAY/YES-DJ
  예·아니오 프로브 3/3, 첫 문장부터 그대로 인용). 전사는 role 별 메시지가 아니라 한 덩어리 텍스트다. ④는 세션 첫 위임
  기준이다 — 이후 위임은 입력 항목이 쌓인다(아래 "백엔드 대화는 누적된다").
  - 결과: 라이브 지시문이 길고 구체적이면 백엔드가 그쪽을 자기 역할로 읽는다. "DJ 모드 틀어줘"에 백엔드가 `end_conversation`을
    부르던 실기 사고(2026-10-01, 4회)가 이것 — 라이브 지시문 없이 오프라인 재현하면 어떤 변형도 `start_dj` 5/5, 라이브 지시문을
    developer 로 넣고 재현하면(none) 첫 턴 8/20, 대화 3턴 뒤 끝이 "고마워" 4/20, 끝이 "아니 됐어" **0/20**(19회 end_conversation).
    즉 첫 턴만의 문제가 아니라 전사가 마무리 분위기면 더 심하다. 인사 1턴 뒤처럼 짧고 중립적이면 20/20. 프로브 지시를 무시하고
    "DJ 모드로 전환할게요"라고 *레이처럼* 답한 사례도 같은 증상. 위 "web search 쓰지 마라 무시됨"도 같은 원인일 가능성.
  - **왜 DJ 에서 드러났나**: DJ 모드로 라이브 지시문이 455 → 1,070 토큰(백엔드 자기 지시문 643 보다 큼), 종료·정지 어휘
    (end/stop/over)가 4 → 17회, 위임 조건 목록이 두 벌. 백엔드 모델·추론 설정(gpt-5.4-mini, none)은 9/29 부터 같았고 이야기
    모드에선 오발이 없었다. 지시문 문구·구조 변형(역할 분리, 태그, 마크다운 위계, 135행 모순 삭제)은 none 에서 전부
    4~6/10 범위로 효과 없음. 라이브 `# DJ mode` 절 제거만 6/8 → 3/8. 라이브 지시문을 뺄 수는 없으므로 추론 low 로 해결.
  - **원인은 판단이 아니라 툴 선택 미끄러짐**: 오발 뒤 백엔드에 물으면 "end_conversation 을 부르지 말았어야 했다, start_dj 가
    맞다"고 답한다. 라이브 지시문의 goodbye 줄을 빼도 그대로. 오답은 **툴 목록의 첫 함수 툴**로 쏠린다(end_conversation 을 맨
    뒤로 보내면 오답이 새 첫 툴 search_memory 로 이동, 6/10). 순서는 해결책이 아니다.
  - **추론 `none` → `low` 로 해결**: 첫 턴 DJ 요청 10/10, 작별·볼륨·날씨·곡 지정 각 5/5, 지연 차이 없음(1.1~2.4 s 동일).
    Pi 에서 직접 호출로 확인한 추론 토큰: DJ 요청 none 0 / low 0~15, 날씨 none 26~42(!) / low 14~40 — web search 경로는
    none 이어도 추론이 돈다. 지연 편차(0.9~2.5 s)는 추론이 아니라 API 왕복 쪽. 운영은 low (`wiring._LIVE_BACKEND_REASONING`).
- **client 모드 지연 (2026-10-02, 하네스 client-demo 를 진짜 Responses 호출로 바꿔 측정, 둘 다 none, 위임 생성 → 첫 음성)**:
  DJ 진입 responses 1.2 s vs client 2.0~3.1 s, 날씨 responses 1.5~2.1 s vs client 3.2~7.1 s. client 는 Pi→API 왕복(단순 툴 판단
  1.3 s 중앙값)과 전사 대기·반환 홉이 그대로 얹혀 **+1~2 s, 검색은 그 이상**. 추론 설정으로 줄어드는 성격이 아니다.
  기능은 됨 — `thinking.append(delegation_id)` 로 위임을 조용히 닫아도 모델이 "잠깐만" 없이 진행(3/3), commentary 로 "DJ 모드
  시작됨"을 줘도 읽지 않고 진행(2/2). 결정: 당분간 responses 모드 유지(2026-10-02).
  - **공유 지시문의 포장 (2026-10-02, 마커 지시문 + 예/아니오 프로브 2/2)**: 라이브 지시문은 세 번째 developer 메시지 안에
    **태그 없이** 들어간다("Shared session instructions" 표제 아래 맨몸 텍스트, 앞뒤 60자에 XML 태그 없음). 우리 백엔드 지시문만
    `<backend_delegation_instructions>` 로 감싸인다. 지시문 문자열은 통째로 가므로 `build_live_instructions` 가 붙이는
    프로필·최근 세션 블록도 백엔드에 간다. 표제와 본문 사이의 정확한 연결 문구는 못 봤다 — 전문 인용은 모델이 거부하고,
    "마커 앞 12단어"를 물으면 마커 뒤 단어를 돌려준다(2/2). 즉 백엔드가 보기에 라이브 지시문은 구분 표시 없이 역할 설명 바로
    뒤에 붙은 긴 텍스트이고, 우리 지시문은 태그로 격리된 짧은 블록이다.
  - 프로브 방법: `mic_live.py --delegation responses --probe-backend-input` 에 "받은 입력을 역할 포함 전부 인용" 지시. 전문 인용은
    자주 무시되므로 예/아니오 + 첫 300자 인용이 안정적이다. 백엔드가 web_search 로 빠지지 않는 요청(DJ 요청 + 인사 시드)으로.
- **백엔드 대화는 누적된다 (2026-10-06, `exp_backend_item_persistence.py` + 저장된 응답 `input_items` 조회)**: 백엔드 응답은
  `previous_response_id` 로 바로 앞 백엔드 응답을 잇는다(세션의 첫 응답도 기록되지 않은 이전 응답을 가리킨다). 두 번째 위임의
  입력 항목은 [이전 전사(user) → 앱이 넣은 메시지 → Live 의 `<backend_task>`(developer) → 추론 → 앞 응답의 답(assistant) →
  새 전사(user)] 였고, 새 전사에는 앞 위임 이후의 발화만 들어 있다. `<backend_task>` 첫머리: "Determine the best next step
  based on the provided context. … Return a handoff result for the frontend assistant's thinking context. The fact that this
  request was delegated provides no information about the best next step."
  - **`response.item.create` 로 넣은 메시지는 세션 끝까지 남는다**: 다음 위임 입력에 그대로, 역할도 유지(developer 3/3,
    user 3/3, 대조 0/2). 메시지 역할은 user/assistant/system/developer 를 받고(레퍼런스), developer 도 거부되지 않았다.
- **앱이 부르는 백엔드 응답 (2026-10-06, 실작동 경로 하네스)**: 사용자 발화 없이 `response.create`(필요하면 앞에
  `response.item.create` 메시지)를 보내면 서버가 위임으로 감싼다 — `session.delegation.created` 에 `client_event_id` 가 그
  event_id 로 온다(17/17, 오류 0). 레이 DJ 의 판정 요청이 이 경로다(`GPTLiveSession.request_backend`).
  - **대화 모델은 이것도 자기 위임으로 보고 받는 말을 한다**: 약 0.85~1.0 s 뒤(백엔드 결과보다 먼저), 15/17. "네, 잠시만요",
    "음."처럼 짧은 말이 대부분이지만 엉뚱한 약속도 나온다 — 일반 대화에서 "DJ 모드, 시작해볼게요" 2/6, DJ 판정에서 "지금 곡이
    끝났다고 들어왔어요" 1/7, 판정이 false 인데 "잠시만, 노래 틀어볼게요" 1. 백엔드 텍스트 답은 대화 모델이 말로 옮긴다.
  - **결과 반환과 이어가기를 둘 다 해야 닫힌다**: 함수 결과를 반환하지 않거나 반환만 하고 `response.create` 를 안 보내면
    이후 사용자 요청이 위임되지 않았다(0/4, 관찰 약 10 s). 반환 + 이어가기(백엔드 빈 응답) 3/3, 대조 2/2.
  - append 3종(instructions·thinking·commentary)의 `delegation_id` 는 responses 위임에서 받지 않는다(레퍼런스, "Non-null
    IDs are not accepted with Responses delegation"). 위임 결과를 대화 모델에 직접 넣는 길은 client 모드뿐이다.
- 함수 툴: `tools`에 function 정의 → 백엔드가 호출하면 `output_item.done(type=function_call)` → 우리가 실행 → `response.item.create(function_call_output)` → `response.create` → 백엔드 2차 응답 → 모델 발화. 배터리 조회 예제로 **위임부터 발화까지 약 2.2초.**
- 백엔드 지시문은 답 형식(한국어, 짧게)은 잘 따르지만 "web search 쓰지 마라"는 무시됨. `tool_choice: auto`가 우선하는 듯.
- 모델은 백엔드 답에서 필요한 부분만 골라 자기 말투로 말한다("요청 확인: …" 인용부는 읽지 않음).
- 위임부터 web_search 완료까지 1~2초.
- **종료 툴(`end_conversation`)**: 대화 모델은 툴을 직접 갖지 못하므로 "작별 인사 → 위임 → 백엔드가 툴 호출" 경로만 가능. 대화 모델은 위임과 동시에 자기 작별 인사를 하므로 "기다려 달라"는 대기가 끼지 않았다(11/11). 위임 발생률은 **프롬프트 형식에 크게 좌우**: 규칙을 덧붙여 쓴 프롬프트 3/5, 그걸 "MUST"로 강화 0/3, 공식 템플릿 구조(Backend tools / Delegate when / Do not delegate when)로 정리한 프롬프트 **6/6**. 툴 결과 뒤 `response.create`로 이어가면 백엔드가 작별 인사를 또 만들고 대화 모델이 그걸 한 번 더 말할 수 있어(1/3), 종료 툴일 때는 `response.create`를 생략(인사 1회). 단 위임을 미완으로 두면 `session.close` 뒤 `session.closed`가 **약 9.4초** 뒤에 온다(3/3 일관, 드레인 대기로 추정). 과금(`usage.seconds`)은 close 요청 시점에서 멈추고 오류 이벤트도 없으므로, 레이는 `session.closed`를 기다리지 않고 C++ `playback_complete`만 기다려 SLEEP으로 간다. 이어가는 변형은 close 0.75초지만 인사가 두 번 나옴(2/4).
- **종료 시퀀스 실측**: 툴 호출 → `session.input_audio.mute`(ack 0.24초, 세션 정지 없음) → 출력 0 조각 1초 지속으로 인사 끝 판정(툴 호출 후 4~5초) → `session.close`. 상한 8초. 템플릿 프롬프트에서도 작별 위임 누락 1회 있음(누적 7/9) → 전사 키워드 매칭 폴백 유지.

## 5. 세션 중 텍스트 주입 (append)

세기(1~40) 도중 주입해 발화가 유지되는지 확인. 대조군(주입 없음)은 끝까지 셈.

| 주입 | 표본 | 발화 유지 |
|---|---|---|
| `instructions.append` (영어 전환) | 3 | 0/3 — 즉시 침묵 |
| `instructions.append` (중립: "한국어로 계속") | 1 | 0/1 — 즉시 침묵 |
| `instructions.append` ("끊지 말고 계속" 명시) | 2 | 1/2 — 한 번은 이어짐, 한 번은 세기를 버리고 다른 주제로 |
| `instructions.append` ("계속하되 영어로") | 1 | 0/1 — "I understand—switching to English now." 후 중단 |
| `thinking.append` (사실 주입) | 3 | 2/3 |
| `thinking.append` ("끊지 말고 계속") | 1 | 1/1 |
| `thinking.append` (영어 전환) | 4 | 4/4 — 세기를 이어가며 언어만 전환 |

- **instructions.append는 내용과 무관하게 진행 중 발화를 끊는다.** 지시 자체는 반영된다(이후 영어로 답). 모델이 말하지 않는 틈에 넣어야 한다. 말하는 중인지 알려주는 이벤트가 없으므로 출력 오디오 레벨/전사 유입으로 판단해야 한다.
- **thinking.append는 발화를 유지하며 반영된다.** 언어 전환 같은 발화 방식 변화도 문장 중간에서 자연스럽게 바뀜. 단 강도가 약해, 영어 전환 thinking 후 한국어 질문에는 한국어로 답함(instructions는 규칙, thinking은 참고 정보).
- **주입 사실을 소리 내어 말할 수 있다.** "I'm switching to English now." 등. "조용히 적용하고 언급하지 마라"를 명시해도 2회 중 1회 그대로 말함. 문구로 막을 수 없으니 새어 나가도 되는 표현으로 넣어야 한다.
- ack(`*.appended`)는 0.6~0.7초 뒤에 오고 "주입 수락"만 뜻한다.
- instructions.append는 역으로 **모델의 말을 멈추게 하는 유일한 수단**이다(문서의 가드레일 예시가 이 원리).

## 6. 대화 동작 관찰

- Full-duplex: 사용자 말이 끝나기 전에 "안녕!", "야, 재헌아!" 하고 겹쳐 말함. 사용자가 말을 시작하면 세기를 스스로 멈춤(클라이언트 신호 없음).
- **방 안의 다른 대화에 끼어든다.** "말 걸 때만 답하라"는 지시를 넣어도 주변 대화에 반응. 침묵 강제는 지시로 안 되며 마이크 mute나 세션 종료로 해야 한다. → SLEEP 상태를 GPT-Live 세션으로 대신하기 어렵다.
- 한국어 인식·발화는 대체로 자연스럽다. 이름 "재헌"을 "재혼"으로 발음한 사례 있음. 오인식 사례("날짜가" → "날 차로 친") 있음.
- 시계·날짜 지식이 없고 스스로도 그렇게 말한다. 날짜·뉴스는 백엔드 web_search로 정확히 답함.
- 세션 중 XVF3800 AEC는 정상 동작(스피커 소리에 모델이 반응하지 않음).

## 7. 적용된 사항과 미검증 항목

2026-10-02 코드 대조 기준. 아래 구현 확인은 실기 검증 완료를 뜻하지 않는다.

- SDK 업그레이드·live 전용 루프·무음 보정·C++ 싱크 방어는 적용되어 있다. live 엔진에서는 ASR·VAP·TurnGPT를 로드하지 않는다.
- 프로필·최근 세션은 시작 instructions에 주입하고, 기억 검색은 responses 백엔드의 `search_memory`로 수행한다.
  도입 전 검토했던 검색 기억의 `thinking.append` 직접 주입과는 다르다. 전사는 히스토리·장기기억 입력에 저장한다.
- 볼륨·밝기·노래·DJ 함수 툴이 연결되어 있다. 웨이크워드/SLEEP은 로컬 유지.
- 제약은 남는다: 바지인 때 모델이 스스로 멈추며, 클라이언트 재생 중단이 모델의 발화 인식을 되돌리지는 않는다.
  전사 오인식은 기억에도 들어갈 수 있고, 별도 ASR·LLM·TTS 단계로 성능을 분리 평가하기 어렵다.
- 조각 간격 300 ms 이상일 때 상태를 함께 기록하는 `Audio chunk gap` 로그는 구현되어 있다.

미검증·개선 후보(기존 기록에 완료 근거가 없는 항목):

- [ ] 긴 세션의 컨텍스트 교체 순간(약 40~50분)과 전사 “later corrections” 형태 관찰.
- [ ] 인사 WAV·연결 겹치기의 청취 시작 시간, LED 전환, WAV 끝 → 스트림 전환 실기 확인(§2.2).
- [ ] 재생기 선취 80→40 ms + split 유예 450→560 ms 실험. 당시 OpenAL 선취 추정은 3버퍼×80 ms였으며,
  축소하면 추가 지연 없이 약 110~150 ms 여유를 얻는다는 가설이다. 현재 코드는 80/450 ms 유지.
- [ ] 긴 발화용 파이썬 보정 밴드 축소(목표 +0.1 s, 말 중 문턱 −0.15 s). 현재는 0/−0.3 s 유지.
- [ ] 유선용 시작 여유 100~200 ms 또는 프리버퍼 한 덩이 감소(지연 −360 ms) 실험. 현재는 두 덩이 + 400 ms 고정.
- [ ] 종료 무음 판정 직후 `audio_end`를 보내는 순서 검토. 현재는 close 뒤에 보내며,
  당시 종료 꼬리에 C++가 1.3초를 채운 사례가 있었다.
- [ ] 서버 녹음 대조 스크립트(`verify_live_audio.py` / `analyze_recording.py`) 이관 여부.
  당시 세션 스크래치에만 있었고 현재 `scripts/gpt_live/`에는 없다. 당시 `store: true` 녹음 보존은 30일로 기록됨.
- [ ] 인사말 유도(`instructions.append`)와 사전 WAV 병행, 한국어 이름 발음 제어(IPA) 실험.

장시간 재생의 DAC 드리프트 보정은 [설계 기록의 차후 고려](../../docs/decisions-wip.md#차후-고려)에서 관리한다.

## 8. 실험 도구 사용법

```
uv run python scripts/gpt_live/mic_live.py [옵션]   # 프로젝트 venv (openai 3.x) 로 실행
  --seconds N            최대 실행 시간 (스크립트 모드는 스크립트 끝나면 조기 종료)
  --no-play              스피커 재생 안 함
  --prebuffer-ms N       시작·언더런 후 재생 재개 전 모을 오디오(ms)
  --save out.wav         받은 오디오 저장
  --delegation none|client-demo|responses
  --backend-model M      responses 백엔드 모델 (기본 gpt-5.4-mini)
  --probe-backend-input  백엔드에 "받은 입력을 인용하라" 지시
  --seed "role:text"     시작 히스토리 (반복 가능)
  --script FILE          마이크 대신 TTS 스크립트 입력 (say/wait/instructions/thinking/commentary 줄)
  --instructions "..."   대화 모델 지시문 덮어쓰기
```

로그는 실행마다 `logs/<시각>.log`. ALSA 경고는 `2>&1 | grep -v "^ALSA lib\|^Cannot connect\|^jack server\|^JackShm"`로 걸러서 본다.
