# Working Memory

> 상태: 설계 탐색 단계. 확정된 설계가 아닌 아이디어 정리.

---

## 1. 동기

에피소드 검색(블록 4)은 쿼리 품질에 의존한다. STT 텍스트 기반 쿼리는 부실할 수 있으며, 검색이 못 잡는 맥락이 존재한다. 예: "요즘 좀 나아졌어" — 뭐가 나아졌는지 검색만으로는 알 수 없지만, "최근 논문 마감 스트레스를 받고 있었다"는 맥락이 있으면 LLM이 바로 연결할 수 있다.

검색의 불안정성을 보완하기 위해, 전반적인 맥락을 담은 편집된 요약을 항상 포함하는 방안을 검토한다.

---

## 2. 개념

**Working Memory**: 사용자와의 전체 대화 히스토리에서 핵심을 종합한 서술형 요약. 매 세션 종료 시 갱신하며, 모든 세션에서 항상 주입한다.

### 역할 분담

- **Working Memory**: 숲 — "지금 이 사람에게 무슨 일이 있나", 전반적 맥락
- **에피소드 검색**: 나무 — "그때 그 영화 뭐였지", 구체적 회상

---

## 3. 블록 구성 변경

```
1. System Prompt (정적)
2. User Profile (반정적)
2.5  Working Memory (세션 단위 갱신)     ← 신규
3. Conversation
   ├─ 직전 세션 (에피소드)
   └─ 현재 세션 (턴 로그)
4. Retrieved Memories (상시검색)
```

- Working Memory는 세션 내 고정 → 블록 2 직후 배치로 prefix caching 대상
- 토큰 비용: 1~2문단 (100~200 토큰)

## 4. 프로필과의 관계

### 겹침

프로필(블록 2)과 Working Memory는 담는 정보가 겹칠 수 있다.

- 프로필: "SF 영화를 좋아함" (stable fact)
- Working Memory: "최근에 듄 2를 보고 좋아했다" (temporal context)

### 분리 기준

- **프로필 = 이 사람은 누구인가** (잘 안 변함, fact 단위 관리)
- **Working Memory = 지금 무슨 일이 있나** (매 세션 재작성, 서술형)

### 슬롯 vs 서술 형식 검토

| 기준 | 슬롯 (현재 프로필) | 서술 |
|------|-------------------|------|
| Write 안정성 | 개별 fact APPEND/UPDATE/ABORT, 유실 위험 낮음 | 전체 재작성, LLM이 기존 내용을 빠뜨릴 수 있음 |
| 토큰 효율 | topic::sub_topic 접두사 반복 오버헤드 | 같은 정보를 더 적은 토큰으로 표현 |
| LLM 이해도 | 파싱 가능하나 자연어보다 불리 | LLM이 가장 잘 처리하는 형태 |
| 표현력 | 스키마에 정의된 것만 저장 | 제약 없음 |

슬롯의 유일한 강점은 fact 유실 방지. 나머지는 서술이 우세. Write LLM 품질이 충분하면 서술형 통합도 가능하나, 안정성 우선 시 프로필은 슬롯 유지.

### 절충안

섹션 기반 서술 — 슬롯보다 유연하되, 재작성 범위를 섹션으로 제한하여 유실 리스크 감소:

```
[who]       이 사람은 누구인가 (stable, 거의 안 바뀜)
[interests] 무엇을 좋아하나 (천천히 변함)
[recent]    최근 무슨 일이 있나 (매 세션 갱신)
```

확정 보류. 실제 구현 및 테스트 후 결정.

## 5. 갱신 파이프라인

### 입력

에피소드 + 기존 Working Memory → LLM → 새 Working Memory.

프로필 fact도 에피소드에서 추출하므로 동일 소스. Raw 대화를 입력으로 쓰면 뉘앙스/톤을 더 잡을 수 있으나, 에피소드 기반으로 시작하고 부족하면 전환.

### 블록 3 비동기 요약을 통한 Write 파이프라인 단순화

현재 설계는 세션 종료 후 raw 원문을 윈도우 분할하여 에피소드를 추출한다. 대안으로, 세션 중 블록 3을 비동기 요약으로 압축하면 세션 종료 시 블록 3 자체를 Write 입력으로 재활용할 수 있다.

**현재 (절삭 + 윈도우 방식)**:
```
세션 중: 블록 3 토큰 초과 → 오래된 턴 제거 (절삭)
세션 후: Raw 원문 → 윈도우 분할 → 윈도우별 추출 → 중복 해소 → 에피소드
```

**대안 (비동기 요약 방식)**:
```
세션 중: 블록 3 토큰 임계치 도달 → 비동기로 0~N번 턴 요약
         → 요약 완료 시 0~N번 턴을 요약으로 교체
         → 다시 차면 반복 (기존 요약 + 다음 구간 → 새 요약)
세션 후: 블록 3 (요약 + 최근 원문) → 에피소드 + fact 추출 (1회)
```

| | 윈도우 방식 | 비동기 요약 방식 |
|---|---|---|
| Write 입력 | Raw 원문 (윈도우 분할) | 블록 3 (이미 토큰 내) |
| LLM 호출 | 윈도우 수 × 추출 + 중복 해소 | 1회 추출 |
| 복잡도 | 윈도우 크기, 겹침, 중복 판정 | 없음 |
| 정보 손실 | 윈도우 경계 맥락 절단 | 중간 요약 시 압축 손실 |
| 이점 | 원문 보존 | 파이프라인 단순화, 맥락 보존 요약 |

비동기 요약은 토큰 비율 기반으로 요약 범위를 결정하며, 임계치 도달 전 여유 있을 때 시작하여 latency 영향을 최소화한다.
