## 1. 시스템 특성

### 사전 호출 (Turn Shift) 구조
- 별도 턴테이킹 모듈이 사용자 발화 종료를 예측
- 종료 판정 전, "끝난 것 같은" 시점마다 STT 텍스트로 LLM 생성 시작
- 사용자가 계속 말하면 이전 생성 취소, 새 사전생성 실행
- 턴 종료 판정 시 마지막 생성 결과를 사용
- 각 사전생성의 STT 텍스트는 서로 상당히 다를 수 있음 (검색 결과 재사용 어려움)

### 세션
- wakeword로 시작, 종료 명령어로 끝나는 한 번의 대화 단위
- 세션 길이는 가변적

### 임베딩
- 턴테이킹 모듈에서 all-MiniLM-L6-v2 사용 중
- 메모리 검색에도 동일 모델 재사용 가능 (추가 로딩 비용 없음)
- 턴테이킹에서 생성한 임베딩을 메모리 검색에도 재사용 가능

## 2. LLM 인풋 구성

```
┌─────────────────────────────────────┐
│ 1. System Prompt (정적)             │  레이 페르소나, 행동 규칙
├─────────────────────────────────────┤
│ 2. User Context (반정적)            │  매 턴 로드, 비동기 갱신
│   ├ 유저 프로필 (시맨틱 기억)       │  취향, 성격, 관심사
│   └ 관계 메모 (절차적 기억)         │  "이 유저에게는 반말, 짧게"
├─────────────────────────────────────┤
│ 3. Conversation History (동적)      │  이전 세션 요약 + 현재 세션 대화
├─────────────────────────────────────┤
│ 4. Retrieved Memories (상시검색)    │  임계값 필터링 후 주입
│   └ 에피소드 기억                   │  "3일 전 듄 봤다고 함"
├─────────────────────────────────────┤
│ 5. Retrieved Knowledge (미정)       │  외부 DB 검색 결과
│   └ 영화/음악 정보 등               │  별도 설계, tool call 방식 검토 중
└─────────────────────────────────────┘
```

### Prefix Caching
- 블록 1~3은 같은 유저 턴 내 사전생성들 간 동일 → KV 캐시 재사용
- 블록 4(Retrieved Memories)는 맨 뒤에 배치하여 캐시 히트율 극대화

## 3. 메모리 Read 경로

### 에피소드 Read 파이프라인

```
쿼리 구성:
  현재 STT + 직전 N턴 concat (LLM 호출 없이 맥락 보충)

1. 검색 (후보 확보)
   ├ 벡터 검색: all-MiniLM-L6-v2 임베딩 → RAM 벡터 전수 코사인 유사도
   └ BM25 검색: SQLite FTS5 키워드 매칭

2. 리랭크 (순위 결정)
   ├ RRF: 벡터/BM25 결과 합산
   └ Salience: similarity × recency_decay × reinforcement

3. 가지치기 (결과 제한)
   ├ 임계값 필터: 최소 점수 미달 제외
   ├ 메타데이터 필터: 블록 3 세션 제외 등
   └ Top-K: 최대 개수 제한 → 블록 4에 주입

* 그래프 확장, cross-encoder 리랭크 등 추가 옵션은 §7 참조
```

### 프로필 Read (블록 2)
- SQL 조회로 프로필 전체 로드 (슬롯 기반, 토큰 예측 가능)
- 검색 불필요 — 항상 전체 주입

### 저장소

**에피소드 (facts 테이블):**
```
- text: 내러티브 텍스트 (맥락 포함, 대화당 2~5건)
- timestamp: 일시
- session_id: 세션 참조
- embedding: 벡터 (RAM에도 전체 로드)
- reinforcement: 언급 횟수 (salience 계산용)
```

**일반:**
- SQLite: 메모리 텍스트 + 메타데이터 + FTS5 인덱스
- RAM: 앱 시작 시 임베딩 벡터 전체 로드 (.npy 또는 SQLite blob)
- 벡터 용량: 384차원 float32, 1만 건 ~15MB. 전수 검색 < 1ms
- 규모 확장 시 HNSW 등 ANN 인덱스 도입 검토

## 4. 세션 관리

### 세션 종료 시
1. 대화 원문 SQLite 저장 (즉시, 거의 0ms)
2. 세션 요약 생성 (비동기 LLM 호출 후 저장)
3. 메모리 추출/갱신 (비동기/배치, 별도 처리)

### 세션 시작 시 블록 3 구성
```
[블록 3: Conversation History]
--- 이전 세션 요약 (최근 1~2개) ---
(요약 완료된 경우) 요약 텍스트
(요약 미완료 시) 원문 최근 N턴 또는 요약 없이 진행
--- 현재 세션 ---
현재 대화 턴들
```

### 현재 세션 토큰 초과 시
- 슬라이딩 윈도우 (오래된 턴 제거)로 시작
- 필요 시 앞부분 요약 방식 추가 검토

## 5. 메모리 Write 경로

### 기본 원칙
- 대화 중(mid-session) write 없음 — 현재 세션은 히스토리에 있으므로 불필요
- 세션 종료 후 비동기 처리

### 처리 흐름
```
세션 종료
  → 원문 SQLite 저장 (즉시)
  → 원문을 N턴 단위로 청킹
  → 청크별 LLM Extract (병렬 가능):
      출력 1: 프로필 업데이트 (topic::sub_topic)
      출력 2: 에피소드 fact 리스트 (내러티브 텍스트)
  → 프로필 Merge: 슬롯별 APPEND/UPDATE/ABORT (Memobase 방식)
  → 에피소드 Merge: 유사 기존 fact 검색 → ADD/UPDATE/NOOP (Mem0 참고)
  → 임베딩 생성 + RAM 벡터 갱신
  → (옵션) 그래프 엣지 생성 — §7-1 참조
```

## 6. 아키텍처 선정

### 베이스 프로젝트: Memobase

블록 2(User Context)의 프로필 + 관계 메모 관리에 Memobase를 베이스로 사용.

**Memobase에서 가져오는 것:**
- 슬롯 기반 프로필 구조 (topic::sub_topic)
- Extract → Merge 파이프라인 (추출과 병합 판정 분리)
- 프로필 스키마 정의 (어떤 topic을 추출할지 제어)
- 배치 처리 (Buffer Zone)

**커스터마이징:**
- 저장소: PostgreSQL + Redis → SQLite + 인메모리
- Extract 프롬프트: 유저 사실 + 관계 메모(상호작용 선호)를 단일 프롬프트로 추출
  - topic 스키마에 `interaction_style` 등 관계 메모용 카테고리 추가
  - 파이프라인 분리 없이 한번에 처리 (놓치는 경우 발생 시 분리 검토)

**프로필 슬롯 예시:**
```
# 유저 프로필 (시맨틱)
interest::movie: SF, 특히 놀란 감독 [mention 2026/03/23]
basic_info::name: 오*영

# 관계 메모 (절차적)
interaction_style::tone: 반말, 장난투 [mention 2026/03/20]
interaction_style::recommendation: 추천 시 이유를 꼭 설명할 것 [mention 2026/03/22]
```

### 에피소드 메모리 (블록 4)

Memobase를 베이스로 하되, 에피소드는 직접 구현.

**저장:** Fact 단위, 내러티브 스타일 (text + timestamp + session_id + embedding + reinforcement)

**Write:** Memobase Extract 파이프라인을 확장하여 프로필 업데이트 + 에피소드 fact를 동시에 추출.
에피소드 Merge는 Mem0의 CRUD 패턴 참고 (유사 기존 fact 검색 → ADD/UPDATE/NOOP 판정).

**Read:** 벡터 + BM25 하이브리드 → RRF → salience 랭킹 → 임계값 + top-K.
추가 옵션은 §7 참조.

**참고한 프로젝트별 아이디어:**
- Mem0: fact CRUD (ADD/UPDATE/NOOP) — 중복 처리의 기본 패턴
- MemU: salience score (similarity × recency_decay × reinforcement) — 검색 랭킹
- Hindsight: 벡터 + BM25 → RRF(k=60) 검색 파이프라인 참고

## 7. 옵션/확장 후보

확정된 기본 설계와 별도로, 필요 시 추가할 수 있는 옵션들.

### 7-1. 그래프 확장
- SQLite edges 테이블 (source_id, target_id, edge_type, weight)
- temporal (시간 근접) / semantic (임베딩 유사도) 엣지, LLM 불필요
- Read 시 검색된 fact의 1홉 이웃 점수 부스트
- Flat 방식으로 시작하고, 간접 연결 검색이 필요해지면 도입

### 7-2. Cross-encoder 리랭크
- ms-marco-MiniLM-L-6-v2 (~22MB), all-MiniLM과 같은 계열
- RRF 합산 후 후보 5~10개를 정밀 재평가
- 모델 추가 로딩 부담 vs 검색 정밀도 향상 트레이드오프

### 7-3. 백그라운드 쿼리 생성
- 유휴 시간에 LLM으로 정제된 쿼리 생성 → 다음 턴 검색에 보조적 활용
- 토픽 전환 시 임계값 필터링에서 자연 제거

### 7-4. 클러스터 기반 프로필 보강
- 에피소드 fact를 임베딩 유사도로 클러스터링 (numpy, 그래프 불필요)
- 클러스터 전체를 LLM에 넘겨 프로필 슬롯 재평가
- 개별 청크 Extract로는 못 뽑는 교차 세션 통찰 생성
  - 예: 개별 → "듄 좋아함", "인터스텔라 좋아함"
  - 클러스터 → "하드 SF 선호, 시각적으로 웅장한 작품을 좋아함"
- 백그라운드/주기적 실행, 대화 중 파이프라인에 영향 없음

### 7-5. 망각/정리
- fact가 수천 건 이상 쌓이면 검색 품질 저하 가능 (Proactive Interference)
- salience recency_decay가 소프트 망각 역할을 하지만, 한계가 있을 수 있음
- 후보 접근법: 주기적 hard delete (장기 저salience), 프로필 흡수 후 삭제, 유사 fact 병합
- 품질 저하가 관측되는 시점에 도입 검토

### 7-6. 사용자 기억 삭제 요청
- 기본: Write 시 대화에서 삭제/수정 요청을 감지하여 처리. 현재 세션 중 지연은 블록 3(대화 히스토리)이 커버
- 옵션: LLM tool call로 즉시 삭제/플래그 처리

### 7-7. 멀티유저
- 현재는 단일유저 전제
- 멀티유저 시: 테이블에 user_id 컬럼 추가 + 검색 시 필터링
- 또는 유저별 별도 SQLite 파일 (유저 삭제 = 파일 삭제로 격리 가능)
