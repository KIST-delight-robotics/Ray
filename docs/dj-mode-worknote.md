# DJ 모드 작업노트

레이가 라디오 DJ처럼 잔잔한 1인 방송을 진행하는 모드. 소재 하나를 자기 말로 풀고 노래 하나를 틀기를 반복하며,
사용자가 끼어들면 대화 상대로 전환했다가 돌아온다. 진행 중. 끝나면 결정은 `decisions-wip.md`, API 동작 사실은
`scripts/gpt_live/FINDINGS.md` 로 옮긴다.

쓰는 법: **현재 상태**는 코드와 맞게 덮어쓴다(이력은 커밋에). **관찰**은 조건·횟수·결과·스크립트만, 해석 없이.
**가설**은 근거와 반증 조건을 붙이고, 검증되면 관찰·현재 상태로 옮긴 뒤 지운다. **열린 질문**은 사용자가 정한다.

## 현재 상태 (2026-10-07, 곡 자동 재생 반영)

- **진입**: 사용자 요청 → 위임 → 백엔드 `start_dj`. 루프가 결과를 보류하고, 위임 시 모델의 한마디가 끝나 출력 무음
  0.5 s 가 되면 소재 `thinking.append` → 결과 제출 → 이어가기가 오프닝을 시작시킨다. 시작 신호(instructions.append)
  없음.
- **소재**: 대화 모델엔 `thinking.append`(모드 상태 한 줄 + 소재. 누적되므로 "최신 소재만"), 백엔드엔
  `## Current segment` 절(`session.update` 교체, DJ 종료 시 복원). 백엔드에도 넣는 이유: thinking 은 전사에 없어
  사용자 질문이 위임되면 백엔드가 소재를 모른다.
- **라이브 지시문**: 공식 템플릿 구조(정책 절 + `Backend tools` + 위임 정책 한 벌) 뒤에 모드 절, DJ 절은 Talk / Song /
  Listener interruption. 진행 규칙은 여기 상시 — instructions.append 는 500 토큰 한도와 발화 끊김이 있어서.
  진입 예시에 "디제이" 포함.
- **상태의 주인은 루프.** DJ 툴은 세션 내내 노출, 모드 밖 호출엔 오류.
- **곡은 앱이 튼다** (끼어들기 없이 이야기가 끝나는 경우, 루프 `DJWatch`):
  - 이야기는 고정 종료 문구 `"<artist>의 <title>, 들려드릴게요."` 로 끝내고 그 뒤엔 말하지 않게 한다(Song 절).
    곡 소개 뒤 위임 지시는 없다.
  - 소재를 넣은 뒤(진입·다음 소재 모두) **모델의 첫 음성부터** 지켜본다. 출력 전사 **끝**이 종료 문구(띄어쓰기·부호
    제거, 카탈로그 별칭 인정 — `dj.ends_with_closing_line`)이고 무음 **2 s** 면 곡을 튼다(노래 흐름의 무음 추가 대기 생략).
  - 문구 없이 무음 **3 s** 면 판정 요청: `response.item.create`(user 메시지 `DJ_CHECK_MESSAGE`) + `response.create`.
    규칙은 백엔드 지시문 DJ 블록 한 줄 — "이야기가 곡 소개까지 끝났으면 `play_dj_song`, 아니면 빈 응답". 메시지는
    세션 끝까지 백엔드 입력에 남으므로 "이번 요청에만" 이라고 적는다.
  - 판정 위임에서는 `play_dj_song` 외 툴을 실행하지 않고 "빈 응답으로 끝내라" 결과를 돌려준 뒤 이어간다
    (`end_conversation` 으로 세션이 끝나지 않게).
  - 곡이 아니면(빈 응답·텍스트·실패·15 s 무응답) 출력 무음 0.5 s 뒤 `DJ_RETURN_INSTRUCTIONS` → 다음 첫 음성부터 다시
    지켜본다. 이어가기 횟수 상한 없음. 복귀 신호에도 말이 없으면 처리 없음(같은 침묵에 6 s 신호도 안 보냄).
  - 무음은 **받은 무음 조각 길이**로 센다 — 발화 중 네트워크 정지(1.0~1.6 s, 09-17)를 쉼으로 보지 않기 위해.
  - 감시 중 새 사용자 전사가 생기면 그 소재의 감시를 끈다(**임시** — 끼어들기 분기 설계 전까지). 이후는 아래 복귀
    신호와 사용자 요청으로 진행.
  - 사용자 요청 `play_dj_song`(인자 없음 → 현재 소재의 곡)은 그대로. 앱 재생과 겹치면 "already playing".
- **노래 자연 종료** → 다음 소재 thinking + `DJ_SONG_ENDED_INSTRUCTIONS`. **사용자가 노래를 멈추면** DJ 종료.
- **복귀**: DJ 중·노래·위임 없음·사용자와 모델 모두 6 s 무음이면 `DJ_RETURN_INSTRUCTIONS` 한 번(침묵당 1회).
  이야기 끝을 지켜보는 동안(LISTENING/CHECKING)은 보내지 않는다. 모델에겐 "스스로 돌아가지 말라".
- **"잠깐만"·"그만"** 은 둘 다 `stop_dj`(종료). 종료 멘트는 중립("쉬어갈게요"). 재진입 때 이전 소재는 건너뛴다.
- **런타임 검색 안 함**: 이야기는 노트 안에서. 검색은 사용자가 물었을 때만.
- **소재 파일**: `assets/dj_segments/<이름>.md`, frontmatter `song`(카탈로그 키)·`topic`, 본문은 불릿 재료 목록(문장으로
  쓰면 대본이 된다). 곡이 재생 불가면 로드 때 제외. 무작위·DB 기록으로 세션 넘어 중복 회피. 고유명사는 읽는 법을 노트에.
- **유휴 타임아웃 180 s** 그대로.
- **백엔드 추론 low** (eea387a). none 에서 `end_conversation` 오발 — FINDINGS §4.
- **로그**: `DJ: model voice X.XXs after segment push`, `DJ: closing line heard, output quiet …s — playing <곡>`,
  `DJ: stopped without the closing line (…) — asking the backend`, `DJ check finished without a song (…)`,
  `DJ: check gave no song — return signal sent`, `DJ: listener spoke — no automatic song for this segment`,
  `Delegation created (…, by ray_dj_check_N)`.

## 진행 중인 방향: 대본 낭독 + 앱 판정 (실험 중, 운영 미반영)

라이브 모델이 받는 정보와 지시를 줄이고(대화 모델에 부담이 없는 쪽), 끼어들기 판단은 앱이 맡는 쪽으로 바꾸는 중.
아래는 실험과 사용자 결정으로 정한 것이고 코드에는 아직 없다. 실험에서는 "라디오"로 부른다(이름은 열린 질문).

- **대본 전달 — 후보 셋** (근거는 관찰의 "TTS 라디오", "앱 판정기 흐름", "분량 사이 끼어들기", "thinking 앞서 넣기"):
  - **A. TTS**: 앱이 대사를 문장마다 TTS(`gpt-4o-mini-tts`, 라이브와 같은 cedar)로 실시간 송출하고, 라디오 중 모델 출력은
    버린다. 사용자 전사가 오면 TTS 를 멈추고 모델이 대화. 끼어든 순간 한 번 thinking 으로 주제와 마지막 문장을 알린다.
  - **B. commentary**: 대사를 1~2문장 분량으로 `commentary.append`, 받은 무음 조각 1.0 s 마다 다음 분량. 첫 분량 전
    instructions.append 로 `read` 안내("From now on, the application sends you lines to read aloud as commentary, one at
    a time. Read each line as written, slowly and calmly, then stop. Do not add your own words or questions. If the user
    speaks to you, stop reading and talk with them.").
  - **B′. thinking 앞서 넣기**: 대사를 `thinking.append` 로 한 단위 앞서 넣는다 — 모델이 단위 n−1 을 읽기 시작하면
    (전사로 n−2 가 끝났고 n−1 을 넣은 뒤 음성이 나왔으면) 단위 n. 안내 없음. 문구와 단위(문장 / 대사)는 확인 중.
  - 끼어들기 처리는 B′ 가 가장 낫다(분량 사이 끼어들기에도 대답이 망가지지 않고, 맞장구를 모델이 받고 이어 읽는다).
    하지만 B′ 의 대본 충실도는 문구에 따라 크게 흔들린다(대사 밖 글자 중앙 0~1% ~ 20%, 첫머리 군말 21~58%). A 는 대본이
    정확하고 감지 지연에 강하지만 맞장구 처리가 어색하다. B 는 분량 사이 끼어들기의 절반이 망가져 로컬 음성 감지 없이는
    쓰기 어렵다.
- **끼어들기 감지는 앱이 한다** (사용자 결정. 대화 모델에게 위임으로 알리게 하는 방식은 걸리지 않았다).
  - 사용자 입력 전사가 오면 대사 넣기를 보류한다.
  - 판정기: 별도 LLM 호출(`adapters/llm_openai` 의 `OpenAILLM`, gpt-5.4-mini, reasoning none, 구조화 출력)에 "지금
    라디오가 on / paused / off 중 어디여야 하나"를 묻는다. 입력은 낭독 중이던 대사와 끼어든 뒤의 사용자·레이 전사.
    사용자 전사가 0.6 s 멈추면 부르고, 그 뒤 모델이 대사가 아닌 말을 6글자 더 하면 다시 부른다. paused·off 는 오는
    즉시 적용하고, on 은 그 판정 뒤 새 사용자 말도 새 반응도 없을 때만 적용한다. 2.0 s 안에 결과가 없으면 on.
  - 판정 기준(사용자 결정): on = 짧은 반응·감탄이거나 모델이 흘리고 계속 읽음. paused = 그 밖에 레이에게 말을 건 모든 것
    (질문, 자기 이야기, "지루해", "잠깐만", 진행에 대한 질문 "방금 뭐라고 했어?"·"이거 무슨 얘기야?" 포함). off = 그만두자는 말.
  - B: 무음 1.0 s 가 찼는데 지금 대사가 끝까지 전사되지 않았으면(대사 도중 멈춤) 1.5 s 더 기다린다 — 사용자 전사가 올 틈.
- **멈춘 뒤** (사용자 결정): 혼자 다시 시작하지 않는다. 사용자가 이어 달라고 하면 재개, 그대로 두었다가 나중에 "라디오
  해 줘" 하면 새로 시작. 일시정지는 "종료 + 책갈피"로 다룬다(멈춘 뒤의 레이는 일반 대화와 같다). 멈춘 상태에서 판정기를
  계속 돌리지 않는다.
  - 멈출 때 thinking: "Radio talk: paused, because the user started talking to you. Talk with the user now. You do not
    have the rest of the talk; if the user asks to continue the talk or the radio, delegate to the backend to resume it."
  - 재개: 위임 → 백엔드 `resume_radio` → 앱이 아직 읽히지 않은 첫 단위부터 다시 넣는다. 기본 지시문에 Backend tools
    "Radio: starting or resuming the radio talk." 와 위임 목록 "The user asks to start the radio, or to continue a paused
    radio talk." 백엔드 지시에 재개 표현 예("계속해, 이어서 해 줘, 이야기 계속해 줘, 라디오 이어서 해 줘").
- **노래 중** (사용자 결정, 지금 운영과 같음): 레이 말이 출력되지 않으므로 곡 정지 요청에만 위임으로 반응하고 나머지는 무시.
- **"지루해"**: 다음 소재로 넘기지 않고 대화로 받는 쪽(사용자 판단). 처리 방식은 열린 질문.
- **간격**: B 의 무음 1.0 s(들리는 무음 약 1.7 s)는 사용자가 괜찮다고 함. B′ 대사 단위는 문장 쉼 수준(쉼 최대 중앙
  0.3~0.4 s), 문장 단위는 쉼 최대 중앙 1.07 s.
- **라이브 지시문**: 정리본 `scripts/gpt_live/live_instructions_simple.txt` + 라디오 두 줄. 백엔드 지시문 DJ 부분 정리와
  `bench_backend_tools.py` 회귀 확인은 구현 때.
- **실험 도구** (`scripts/gpt_live/`, 결과는 `var/experiments/<실험>/<번호>_<태그>/`, 녹음은 스테레오(왼쪽 사용자, 오른쪽
  로봇) + Audacity 레이블):
  - `exp_dj_commentary_chunks.py` — 분량 주입·덧붙임·쉼·앞서 넣기, `--channel thinking`
  - `exp_barge_in.py` — 발화 출처·안내별 끼어들기 반응
  - `exp_dj_interrupt_reply.py` — 끼어든 말에 대한 대답 (B, 앱 개입 없음)
  - `exp_radio_delegation.py` — 위임으로 끼어들기 감지 (실패한 방식의 기록)
  - `exp_radio_flow.py` — B + 판정기 + 멈춘 뒤 대화·재개, `--interrupt mid|gap`
  - `exp_radio_tts.py` — A, `--release now|decision`
  - `exp_radio_ahead.py` — B′, `--unit sentence|line`
  - `exp_live_conversation.py` — 지시문별 대화·위임 평가

- **위임은 사용자 발화에 대한 응답으로만 생긴다.** 근거: 관찰된 대화 모델의 위임은 모두 사용자 발화 직후. 사용자 발화
  없는 조건(곡 소개 뒤, 앱 신호)은 전부 0. 반증: 사용자 발화 없이 대화 모델이 위임을 1회라도 만듦. (곡 재생은 앱이 맡아
  더 쫓지 않는다.)
- **위임을 요구하는 앱 지시는 무시된다.** 근거: 0/8, 지시에 든 말하기도 수행 안 함. 한계: 문구 1종, 채널은
  instructions.append 만. 반증: 다른 문구·채널(commentary 등)로 위임이 생김.
- **GPT-Live 기본 지시(비공개)가 위임을 사용자 요청에 묶는다.** 위 두 가설의 설명 후보. 직접 검증할 수단은 없다.
- **10-01 실기 17:45 오프닝 재시작은 시작 신호(instructions.append)가 말을 끊은 것.** 근거: 진입 순서 실험의 끊김 시점.
  반증: 시작 신호가 없는 지금도 오프닝 재시작이 나옴.
- **재작성 지시문이 진입 위임을 약하게 한다.** 근거: 재작성 계열 위임 누락 4/50(10-02~07 하네스), 8f0895a 0/6.
  반증: 같은 조건에서 8f0895a 도 비슷한 비율로 누락.
- **라이브 지시문의 `Backend tools` 목록이 백엔드 툴 선택을 돕는다.** 근거: 23/30 대 27~28/30, 유의하지 않음.
- **정지 뒤 "기억 안 남"은 노래 중 들은 곡 음원 때문이다.** 근거: 실기(원본 채널로 곡 36.9 s 입력)와 재현(입력 무음,
  8/8 기억)의 가장 큰 차이. 반증: 노래 중 곡 음원을 입력한 재현에서도 기억함.
- **처음 모른다고 답하면 그 답을 고수한다.** 근거: 실기 첫 질문이 모호("아까 했던 얘기 있잖아") → 되물음 → 다음 질문에서
  처음 "기억 안 남" 뒤 같은 답 반복. 재현은 처음부터 직접 물음. 반증: 실기 순서로 물어도 기억함.
- **모드 분리 지시가 DJ 때 일을 대화 밖으로 취급하게 한다.** 근거: 실기 1회. 재현 조건(기억함)에서는 변형 차이가 없어
  판단 불가. 반증: 증상이 재현되는 조건에서 모드 문장 제거·종료 신호 보강이 효과 없음.
- **commentary 덧붙임은 "전달할 내용"으로 설계된 탓이고, 낭독 틀이 이를 "대본"으로 바꿔 막는다.** 근거: 레퍼런스
  ("context the Live model can communicate", 가이드 "trained to paraphrase"), `read` 6/105 대 낭독 어휘만 바꾼
  `read_talk` 16/56. 반증: 낭독 어휘 없는 문구가 `read` 수준으로 억제.
- **"then stop" 은 덧붙임을 줄이지만 끼어들기 처리를 해친다.** 근거: `say_wait` 19/56 → `say_stop` 8/56, 멈춤 요청 뒤
  계속 읽음 0/4 → 2/4. `read` 는 끼어들기 문장("stop reading and talk with them")이 이를 상쇄하는 후보. 반증: 회차를
  늘려 멈춤 요청 차이가 사라짐.
- **안내에 문장을 더하거나 바꾸면 억제가 약해진다.** 근거: `read_own` 8/56, `read_noread` 12/56 대 `read` 0/56.
  반증: 회차를 늘려 차이가 사라짐 (`read` 도 5/7 회차가 한 번 있었다).
- **낭독 틀이 멈춤 요청에 문장을 마저 끝내게 한다.** 근거: `read` 8/8, 안내 없는 commentary 는 대부분 문장 중간에서 끊음.
  반증: 끼어든 위치를 오디오로 정확히 잰 실험에서 `read` 도 바로 멈추는 경우가 섞임.
- **운영 지시문에 덧붙은 절(DJ·모드 등)이 일반 위임을 약하게 한다.** 근거: 정리본 평가의 작별 0/8 대 8/8, 볼륨·곡
  이름 없는 요청 5/8 대 8/8. 반증: 실기나 다른 표본에서 차이가 없음.
- **위임은 모델이 스스로 할 수 없는 일에만 생긴다.** 근거: 라디오 중 말 걸기·"잠깐만"·"그만하자" 위임 0/17(모델은
  "네, 멈출게요"라고 말만 함), 노래 질문 3/4, 재개는 "나머지 이야기는 너에게 없다"고 알린 뒤 "라디오 …" 요청 B·A 86/86,
  B′ 23/25.
  반증: 모델이 혼자 할 수 있는 일(대답·멈춤)에 대해 앱 규칙만으로 위임이 안정적으로 생김.
- **thinking 은 읽을 거리가 쌓여 있으면 그대로 읽고, 쉬다가 받으면 소재로 삼아 지어낸다.** 근거: 쉬는 모델에 한 줄씩
  32/56 덧붙임 대 앞서 넣기 회차 전체 0.97~1.07배, TTS 와 나란히 읽은 시험 0.97~1.08배. 반증: 쉬는 모델에게 한 줄씩 줘도
  그대로 읽는 조건이 나옴.
- **모델은 문장 경계에서 가장 최근에 받은 줄로 넘어간다.** 근거: commentary 앞서 넣기에서 하던 분량의 나머지를 버림 2/2,
  thinking 대사 단위 앞서 넣기에서 둘째 문장 건너뜀 15/57(버그 섞임), 같은 문구에서 문장 단위 4/19 대 대사 단위 9/19.
  한계: s2·l2 는 문구 탓에 군말·대사 밖 말이 많아 건너뛰기만 따로 보기 어렵다. 반증: 군말이 없는 문구에서 문장 단위로
  앞서 넣어도 건너뛰기가 줄지 않음.
- **thinking 은 말하기를 강제하지 않아, 대기 줄이 있어도 사용자 말에 먼저 답한다.** 근거: B′ 대답 전 새 대사 0/32 대 B
  (commentary) 분량 사이 끼어들기 13/26. 반증: B′ 의 분량 사이 끼어들기를 늘려 대기 줄을 먼저 읽는 경우가 나옴.
- **기본 지시문에 라디오 줄을 더하면 commentary 덧붙임이 는다.** 근거: f2·f3 18~19% 대 같은 날 라디오 줄 없는 대조 7%.
  한계: f1(같은 지시문)은 10%, r1(라디오 줄 없음) 6% — 날짜에 따른 변동이 섞임. 반증: 같은 날 두 지시문을 나란히 돌려
  차이가 없음.
- **맥락·상태 문구가 라디오를 남의 일처럼 말하게 한다.** 근거: A 의 "played by the application" → "재생되고 있었어요",
  A 질문 대답의 라디오·멈춤 언급 14/43. 반증: 레이 자신의 말로만 쓴 문구에서도 같은 비율.
- **"라디오"가 지시문(Backend tools 의 Radio 줄)과 대사 문구에 함께 있으면, 모델은 그것을 따로 트는 방송으로 여긴다.**
  근거: "On the radio you are now saying" 문구가 라디오 줄 없는 지시문(th_ahead)에선 군말 1/4·회차 전체 0.97~1.07배였는데,
  라디오 줄 있는 지시문(s2·l2)에선 군말 21/38("라디오 다시 켰어요", "지금 라디오에서는 …"), 대사 밖 글자 중앙 5~20%.
  "Next line of your radio talk"(a1·ag1, 라디오 줄 있음)는 군말 12/57, 대사 밖 0~1%. 반증: 라디오 줄을 빼거나 대사
  문구에서 "radio" 를 빼도 군말이 같음.

## 열린 질문

- **대본 전달 방식**: A(TTS) / B′(thinking 앞서 넣기). B 는 로컬 음성 감지 없이는 분량 사이 끼어들기를 감당 못 함.
  B′: 대사 문구(레이 자신의 말로 읽히고 "라디오"를 외부 방송으로 여기지 않게 — 모델용 지시문·문구에서 "radio" 를 뺄지),
  단위(문장 / 대사)와 건너뛰기, thinking 에 맞춘 라디오 시작 안내가 필요한지, 전사로 진행을 놓쳤을 때 앱이 어디서 재개할지.
- **A 의 맞장구 처리**: (가) 감지되면 TTS 소리만 낮추고 판정 — on 이면 그대로 이어 가고 모델 말은 버림 / (나) 지금처럼
  멈추되 첫 마디에서 끊고 다음 문장부터. 라디오·멈춤 언급(14/43) 줄이기.
- **"지루해" 처리**: 대화로 받는 쪽. 다른 이야기·노래·그만두기를 되묻게 할지, 그 지시를 어디에 둘지(멈춤 thinking 등).
- **책갈피 수명**: 세션 끝·새 라디오 시작 때 버리기(제안), 시간 기준을 둘지.
- **이름**: DJ / 라디오(사용자 표현은 "라디오 모드", 제안은 라디오). 내부 이름 변경은 구현 때.
- **판정기 평가**: 직접 쓴 TTS 발화라 정확도는 참고치. 판정기 입력·출력을 남겨 실기 기록으로 오프라인 재평가.
- **아직 안 잰 것**: 한 세션에서 멈춤·재개 여러 번(thinking 누적), 곡 소개 대사·곡 전환 중 끼어들기, 운영 백엔드 툴과의
  공존(`bench_backend_tools.py`), 재개 위임에 백엔드가 툴을 안 부를 때의 처리, 멈춘 뒤 대화·재개 요청의 표현 다양화.
- **실기에서만**: 로컬 음성 감지(XVF3800 AEC 신호)의 정확도·지연, 에코·주변 말소리로 생기는 잘못된 보류, A 의 TTS 에코.
- **끼어든 질문에 대한 대답의 자기 설정**: "넣진 못하지만" / "넣어둬요" / "마음을 넣어둔다" 가 엇갈림, 반말 질문에 반말.
- **B 를 쓴다면**: `read` 의 비용(멈춤 요청에 문장을 마저 끝냄 1~2 s, 낭독 어휘 노출 2/35), 대사를 마저 읽고 늦게 대답
  (4.5 s+ 3/42).
- **노래 정지 뒤 "기억 안 남"** (실기 1회, 재현 안 됨). 다음 재현 후보: 노래 중 곡 음원 입력, DJ 전 대화, 실기 질문 순서.
- **DJ 종료 뒤 할 수 없는 약속**: "다음 이야기로 넘어가볼게요" 뒤 아무것도 없음.
- **진입 실패**: 위임 누락·요청 못 들음 (10-06 자동 재생 실험 각 2/16).
- **판정 경로**: 공백 5~8 s, 엉뚱한 받는 말 2/7, 판정 메시지가 백엔드 입력에 세션 끝까지 쌓임(이후 요청 영향 미측정).
- **단위 테스트로만 확인한 경로**: 판정 뒤 복귀 신호로 이어가기, 이야기 중간에 멈춘 실제 상황, 판정 중 잘못된 툴,
  15 s 무응답, 모델 자신의 `play_dj_song` 과 앱 재생의 겹침.
- 매 소재 같은 종료 문장의 느낌 (청취로 판단).
- 실기 확인: 끼어들기·복귀, 종료 경로("그만", 노래 중 "꺼줘", 종료 키워드), DJ 발화가 장기기억 에피소드로 추출되는지
  (필요하면 DJ 중 assistant 전사는 저장 제외).
- 이후 과제: "잠깐만" 뒤 이어가기, 노래 중 "다음 곡", 소재 작성 방식(직접 vs 큰 모델 초안 + 검토)과 노트 밀도 기준.
