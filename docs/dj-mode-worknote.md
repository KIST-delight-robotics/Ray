# 라디오(구 DJ) 모드 작업노트

레이가 잔잔한 1인 라디오를 진행하는 모드. 준비된 대본을 대사 하나씩 읽고 곡 하나를 틀기를 반복하며, 사용자가
끼어들면 대화 상대로 전환했다가 이어 달라면 돌아온다. 처음엔 모델이 소재 노트로 이야기를 지어내는 DJ 모드였고,
지금은 대본 낭독(B′) + 앱 판정으로 운영 코드에 들어갔다(fca2b8a). 진행 중. 끝나면 결정은 `decisions-wip.md`, API 동작
사실은 `scripts/gpt_live/FINDINGS.md` 로 옮긴다.

쓰는 법: **현재 상태**는 코드와 맞게 덮어쓴다(이력은 커밋에). **관찰**은 조건·횟수·결과·스크립트만, 해석 없이.
**가설**은 근거와 반증 조건을 붙이고, 검증되면 관찰·현재 상태로 옮긴 뒤 지운다. **열린 질문**은 사용자가 정한다.

## 현재 상태 (2026-10-12, 라디오 운영 반영)

코드는 `engines/gpt_live/radio.py`(대본·추적·판정기·상태, I/O 없음)와 `loop.py` 의 연결 고리. 근거는 관찰 — 특히
"thinking 앞서 넣기", "운영 순서 시작", "긴 대본", "추적 규칙 재생 평가", "운영 경로 라디오".

- **대본**: `assets/radio_scripts/<이름>.md`, frontmatter `song`(카탈로그 키)·`topic`, 본문은 한 줄에 대사 하나(1~2문장),
  마지막 대사가 곡 소개. 곡이 재생 불가면 로드 때 제외, 무작위·DB(`radio_script_plays`)로 세션 넘어 중복 회피. 불러올 때
  작성 규칙을 검사해 경고만 한다(`check_script`: 1~2문장, 마지막 문장 13자 초과(곡 소개 대사 빼고), 앞뒤 두 대사 안에 8자
  넘는 같은 구절 없음, 숫자·로마자 없음). 대본은 순서와 상관없이 쓰고 시간대를 단정하지 않는다 — 곡 뒤 대본이면 앱이 첫
  대사 앞에 "노래 잘 들으셨어요?" 를 붙인다. 첫 대사는 시작 한마디("~해 볼게요")와 겹치지 않게.
- **시작**: "라디오 해 줘"(백엔드 예: 라디오, 디제이, DJ, 혼자 진행) → 위임 → 백엔드 `start_radio` → 그 자리에서 대본을
  고르고 첫 대사 `thinking.append`("You are now saying: «…»") → 결과 `{"status": "on"}` → 이어가기(백엔드는 빈 응답).
  백엔드 지시문 끝 `## Radio talk` 절의 상태를 on 으로 갱신. 함수 호출은 백엔드 응답이 끝난 뒤 실행되므로 첫 대사는
  호출 순간보다 약 0.3 s 늦게 들어간다(실험은 호출 순간).
- **진행(`Tracker`)**: 출력 전사를 대본과 8자 이상 일치로 따라간다. 다음 대사는 지금 대사의 마지막 문장에 들어서 남은
  글자가 13자 이하일 때 — 앞서 넣는 근거는 이 일치뿐이다. 넣은 뒤 말하고 받은 무음 조각이 1.5 s 면 멈춘 것: 마지막 일치
  뒤로 대사 끝까지 8자 이상 남았고 그 뒤 말한 글자가 남은 양의 절반 미만이면 끊긴 문장부터 한 번 다시 넣고, 그 밖이나
  다시 넣은 지 3 s 가 지나도 조용하면 다음 대사. 끝난 대사 수는 전사 조각마다 센다(보류 중에도).
- **곡**: 곡 소개 대사를 끝까지 읽고 0.5 s 조용하면 노래 흐름을 툴 결과 없이 탄다(스트림을 닫으니 덧붙임은 잘린다).
  끝을 못 찾으면 말한 뒤 4 s 조용할 때(다시 넣었으면 3 s 지난 뒤), 마지막 대사를 넣고 60 s 면 그냥 곡. 자연 종료 → 다음
  대본 첫 대사(곡이 끝났다는 instructions 신호 없음). 사용자가 곡을 멈추면 라디오 종료(종료 문구 + 노래 종료 지시).
- **끼어들기**: 라디오 on 중 사용자 전사가 오면 보류(넣기·멈춤 판단 중지). 판정기(`RadioJudge`, gpt-5.4-mini, 추론 없음,
  구조화 출력, 입력 = 읽던 대사 + 사용자 전사 1.3 s 전부터의 사용자·레이 전사)를 사용자 전사가 0.6 s 멈추면 부르고,
  모델이 대본 밖 말을 6자 더 하면 다시 부른다. paused·off 는 오는 즉시, on 은 그 판정 뒤 새 사용자 말·새 반응이 없을 때
  적용. 2 s 안에 답이 없으면 on(늦게 온 paused·off 는 적용). 판정을 기다리지 않는데 10 s 조용하면 보류를 푼다. on 뒤
  모델 말은 대본과 다시 8자 일치할 때까지 "말한 글자"에서 뺀다.
- **멈춤·재개**: paused → thinking "Radio talk: paused, … Do not continue the talk yourself: the rest of it is not with
  you. If the user asks to go on with it (for example 계속해, 이어서 해 줘, 이야기 계속해 줘), delegate to the backend to
  resume it." + 백엔드 상태 paused. 멈춘 동안의 대화는 진행 계산에 넣지 않는다. 재개 → `resume_radio` → "Radio talk:
  resumed. …" + 안 읽힌 첫 대사부터 다시 넣는다. 멈춘 상태에서 `start_radio` 는 새 대본(재개 문구를 함께 넣는다, 실험
  안 함). off(판정·곡 정지) → "Radio talk: ended. Talk with the user now." + 상태 off. 노래 중엔 라디오를 돌리지 않는다.
- **지시문**: 라이브는 정리본(`live_instructions_simple.txt` 와 같은 내용) + Backend tools "Radio: your own radio talk,
  which you host and speak yourself. Starting it, or resuming it after a pause." + 위임 목록 "The user asks to start the
  radio, or to continue a paused radio talk." 진행 규칙은 대화 모델에 없다. 백엔드는 Task instructions 의 Radio 블록 +
  `## Radio talk` 상태 절.
- **정한 것** (사용자 결정, 근거는 관찰):
  - DJ 모드를 통째로 대체, 이름은 라디오, 대본은 시간대를 가리지 않게(10-12).
  - 대본 전달은 B′(thinking 앞서 넣기, 10-12). A(TTS)는 대본이 정확하고 감지 지연에 강하지만 맞장구 처리가 어색하고
    모델 대답과 TTS 를 오가는 이음매가 들린다. B(commentary)는 덧붙임이 많고 대사 사이 끼어들기의 절반이 망가져 로컬
    음성 감지 없이는 쓰기 어렵다. B′ 의 구조적 비용: 이미 넣은 대사는 모델이 알아, 끼어든 뒤 읽던 대사의 나머지를
    읽거나 대답에 섞는다.
  - 끼어들기 감지는 앱의 판정기(대화 모델에게 위임으로 알리게 하는 방식은 걸리지 않았다). 판정 기준: on = 짧은 반응·
    감탄이거나 모델이 흘리고 계속 읽음, paused = 그 밖에 레이에게 말을 건 모든 것(질문, 자기 이야기, "지루해", "잠깐만",
    "방금 뭐라고 했어?" 같은 진행 질문 포함), off = 그만두자는 말.
  - 멈춘 뒤 혼자 다시 시작하지 않는다. 이어 달라면 재개, 그대로 두었다가 나중에 "라디오 해 줘" 하면 새로 시작 —
    일시정지는 "종료 + 책갈피", 멈춘 뒤의 레이는 일반 대화와 같다. 멈춘 동안 판정기를 돌리지 않는다.
  - 노래 중엔 레이 말이 나가지 않으므로 곡 정지 요청에만 반응한다. "지루해"는 다음 소재로 넘기지 않고 대화로 받는다.
  - 대사 사이 쉼(앞 대사 끝 → 다음 대사 첫 글자 중앙 약 1 s)은 괜찮다.
  - 앞서 넣기의 근거는 8자 일치뿐, 모르면 무음을 기다린다. 멈춘 뒤엔 확실히 안 말한 것만 다시 넣고 어미 몇 자는
    넘어간다. on 뒤 대답은 다시 일치할 때까지 진행에서 뺀다(10-12, 관찰 "추적 규칙 재생 평가").
  - 이번 범위 밖: 진입 위임 누락·완전 침묵 폴백, 로컬 음성 감지(10-12).
- **유휴 타임아웃 180 s** 그대로. **백엔드 추론 low**.
- **로그**: `Radio started: <대본> (song …)`, `Radio: line N/M pushed (start|text|stall|resume)`, `Radio: quiet after

  (<이유>)`, `Radio: <상태> by the judge`, `Radio: hold released (judge on|judge timeout|quiet)`, `Radio: song introduced

  - `radio_replay.py` — API 없이 기존 결과(radio_ahead l4~l11c, radio_long)로 추적·넣기·멈춤 규칙을 다시 돌려 사후
    정답(전사 전체를 대본에 아핀 갭 정렬)과 비교. `validate`, `push`, `stall`, `pauses`, `done`, `production`(운영

  - `bench_backend_tools.py` — 백엔드 툴 선택(라디오 상태별 케이스 포함), `exp_live_conversation.py` — 일반 대화·위임
  - 실험용 직접 세션(운영 코드와 규칙이 다르다 — 5자 일치·받침 신호·남은 2자): `exp_radio_ahead.py`(B′, 끼어들기),
    `exp_radio_long.py`(긴 대본), `exp_radio_flow.py`(B + 판정기), `exp_radio_tts.py`(A), `exp_dj_commentary_chunks.py`,
    `exp_barge_in.py`, `exp_dj_interrupt_reply.py`, `exp_radio_delegation.py`. DJ 시절 하네스 실험(`exp_dj_autoplay.py`,
    `exp_dj_after_stop.py`, `exp_dj_song_delegation.py`)은 fca2b8a 에서 지웠다
  - 회차는 목적에 맞게 정한다. 수치를 재는 실험과 운영 코드가 같게 도는지 보는 확인은 다르다 — 확인은 조건당 3회 안팎.
    GPT-Live 는 연결 시간 분당 $0.05. 하네스 실험은 프로세스마다 약 850 MB 라 이 PC 에선 동시에 둘. 실험을 제안할 때
    예상 비용을 함께 적는다

## 가설

- **위임은 사용자 발화에 대한 응답으로만 생긴다.** 근거: 관찰된 대화 모델의 위임은 모두 사용자 발화 직후. 사용자 발화
  없는 조건(곡 소개 뒤, 앱 신호)은 전부 0. 반증: 사용자 발화 없이 대화 모델이 위임을 1회라도 만듦. (곡 재생은 앱이 맡아
  더 쫓지 않는다.)
- **위임을 요구하는 앱 지시는 무시된다.** 근거: 0/8, 지시에 든 말하기도 수행 안 함. 한계: 문구 1종, 채널은
  instructions.append 만. 반증: 다른 문구·채널(commentary 등)로 위임이 생김.
- **GPT-Live 기본 지시(비공개)가 위임을 사용자 요청에 묶는다.** 위 두 가설의 설명 후보. 직접 검증할 수단은 없다.
- **10-01 실기 17:45 오프닝 재시작은 시작 신호(instructions.append)가 말을 끊은 것.** 근거: 진입 순서 실험의 끊김 시점.
  반증: 시작 신호가 없는 지금도 오프닝 재시작이 나옴.
- **재작성 지시문이 진입 위임을 약하게 한다.** 근거: 재작성 계열 위임 누락 4/50(10-02~07 하네스), 8f0895a 0/6.
  반증: 같은 조건에서 8f0895a 도 비슷한 비율로 누락.
- **라이브 지시문의 `Backend tools` 목록이 백엔드 툴 선택을 돕는다.** 근거: 23/30 대 27~28/30, 유의하지 않음.
- **정지 뒤 "기억 안 남"은 노래 중 들은 곡 음원 때문이다.** 근거: 실기(원본 채널로 곡 36.9 s 입력)와 재현(입력 무음,
  8/8 기억)의 가장 큰 차이. 반증: 노래 중 곡 음원을 입력한 재현에서도 기억함.
- **처음 모른다고 답하면 그 답을 고수한다.** 근거: 실기 첫 질문이 모호("아까 했던 얘기 있잖아") → 되물음 → 다음 질문에서
  처음 "기억 안 남" 뒤 같은 답 반복. 재현은 처음부터 직접 물음. 반증: 실기 순서로 물어도 기억함.
- **모드 분리 지시가 DJ 때 일을 대화 밖으로 취급하게 한다.** 근거: 실기 1회. 재현 조건(기억함)에서는 변형 차이가 없어
  판단 불가. 반증: 증상이 재현되는 조건에서 모드 문장 제거·종료 신호 보강이 효과 없음.
- **commentary 덧붙임은 "전달할 내용"으로 설계된 탓이고, 낭독 틀이 이를 "대본"으로 바꿔 막는다.** 근거: 레퍼런스
  ("context the Live model can communicate", 가이드 "trained to paraphrase"), `read` 6/105 대 낭독 어휘만 바꾼
  `read_talk` 16/56. 반증: 낭독 어휘 없는 문구가 `read` 수준으로 억제.

- **안내에 문장을 더하거나 바꾸면 억제가 약해진다.** 근거: `read_own` 8/56, `read_noread` 12/56 대 `read` 0/56.
