# ReSpeaker 마이크

> 2026-09 ~ 2026-10 ReSpeaker 마이크 작업의 기록. 완료 후 고정 — 이후 변경은 반영하지 않는다.

## 개요

ReSpeaker(XVF3800) 마이크를 대화에 쓰면서 부딪힌 문제를 다룬 작업이다. 파이프라인 시작 때 펌웨어를
소프트웨어로 리셋하는 것에서 시작했다(2026-09-18). 이후 GPT-Live 대화에서 사용자가 끼어든 말이 한 음절로
잘리는 현상이 있었다. 이를 진단하려고 채널별 녹음을 넣었고, 원인은 XVF3800 의 에코 제거 이상 상태였다(2026-10-13).
마지막으로 마이크 입력을 후처리 없는 CH1 한 채널로 통일했다(2026-10-14).

관련 조사 기록 (계속 갱신되는 문서):
- [respeaker-aec-degradation.md](../troubleshooting/respeaker-aec-degradation.md) — 에코 제거 이상 상태

## 시작 시 소프트웨어 리셋 — main() 첫 줄, 대기 없음, fail-open (2026-09-18)

XVF3800 펌웨어를 USB 벤더 명령(REBOOT, resid 48 / cmdid 7)으로 재시작한다. 파이프라인 시작마다 한 번 보내
마이크를 알려진 상태에서 시작한다. 보드 RST 버튼(하드웨어 리셋)과 효과가 같지는 않다 — 아래 AEC 이상 상태 절.

- **호출 위치는 `main()` 첫 줄**: 리셋 후 재열거까지 실측 USB 0.97 s, ALSA 0.99 s, PyAudio 1.11 s다.
  Python 시작에서 "Pipeline starting" 까지 약 21 s(임포트 + 모델 로딩)가 걸리므로 그 앞에 두면 대기가 필요 없다.
  `audio_input.start()` 직전에는 존재 폴링 가드(상한 3 s)만 두며, 정상 경로에서는 즉시 통과한다.
- **부팅 순서 충돌 없음**: 부팅 후 시점은 다음과 같다.
  - 커널 USB 인식 +1.5 s, snd-usb-audio +6.8 s
  - 유저 서비스(PipeWire·ray-python) +17 s
  - ray-cpp 는 PWM 게이트 뒤 +24 s

  리셋 시점(+17~19 s)에 마이크는 안정 상태고 C++ 는 아직 안 떠 있다.
- **C++ 스피커 출력과 공존**: ReSpeaker 는 스피커 겸용이고 C++ 가 PipeWire 기본 싱크로 재생한다. 재생 중
  리셋을 실측했다.
  - 스트림은 살아 있었다. 1 s 뒤 HDMI 로 옮겨졌다가 3 s 안에 ReSpeaker 싱크로 자동 복귀했고, 기본 싱크도 유지됐다.
  - 시작 시점에는 재생이 없어 영향이 없다. Python 만 수동 재시작해도 같은 이유로 안전하다.
- **fail-open**: 장치 없음·pyusb 없음·권한 거부 모두 경고 후 진행한다.
  - 권한은 udev 규칙으로 준다([SETUP.md](../SETUP.md) §11). 기본 노드가 `root:root 664` 라 쓰기가 거부되기 때문이다.
  - 규칙이 부팅 열거에도 적용되는 것을 확인했다.
- **외부 저장소를 import 하지 않음**: Seeed `xvf_host.py` 는 파라미터 표 전체와 CLI 를 담고 있어, REBOOT 한 줄만
  어댑터에 옮겼다.
- **함정 — 리셋은 파라미터를 기본값으로 되돌린다**: 이후 XVF3800 파라미터를 쓰게 되면 리셋 뒤에 재적용해야 한다.

## 마이크 채널별 녹음 (`MIC_DUMP`) — AEC 진단용, 캡처 스레드 안에서 (2026-10-13)

- **파이프라인 안에서 남기는 이유**: `AudioInput` 이 reSpeaker 를 `hw:1,0` 으로 단독으로 열기 때문에, 실행 중에는
  다른 프로세스가 같은 마이크를 녹음할 수 없다. 실제 대화 조건(C++ 재생 경로·볼륨·GPT-Live 음성)을 담으려면 캡처
  스레드가 읽은 프레임을 그대로 쓰는 수밖에 없다.
- **채널 추출 전의 전 채널을 남긴다**: GPT-Live 가 받는 CH0 하나로는 "칩이 억제했다" 와 "모델이 짧게 받아들였다" 를
  가를 수 없다. 원본 마이크(CH2–5)와 ASR 출력(CH1)을 같은 시간축에 두어야 비교된다.
- **채널별 mono, 게인 없음**:
  - 6ch WAV 는 일반 플레이어가 5.1 로 다운믹스해 CH0·CH1 이 섞여 들린다. 그래서 채널마다 mono 로 저장한다.
  - 원본 채널은 −75 dBFS 안팎이라 키워서 저장하고 싶어진다. 그러나 그러면 레벨 정보가 사라지고, 원본이 커지면
    클리핑한다. 저장은 그대로 하고, 키운 사본은 들을 때만 만든다.
- **들을 파일은 `ray.wav` 로 따로**: 채널 파일은 측정용이라 작아서 안 들린다. 큐에 넣는 mono(추출 채널 × 게인)를
  같은 폴더에 함께 써서, 사본 없이 "레이가 들은 소리" 를 바로 듣는다. 추출 채널·게인을 바꿔도 저장 쪽은 고칠
  필요가 없다.
- **강제 종료에도 유효**: `wave.writeframes` 가 매번 헤더를 고쳐 쓰기 때문에, Ctrl+C 로 끊은 녹음도 그대로 쓸 수 있었다.
- **진단 때만 켠다**: 프로세스 수명 동안 녹음하고(SLEEP 포함), 6ch + `ray.wav` 로 분당 ~13.4 MB 가 쌓인다.

## AEC 이상 상태 — 당분간 수동 전원 재투입, REBOOT 는 유지 (2026-10-13)

조사 기록은 [respeaker-aec-degradation.md](../troubleshooting/respeaker-aec-degradation.md)에 있다. 더블토크 때
사용자 말이 한 음절로 잘리던 원인은 XVF3800 의 에코 제거 이상 상태였고, 물리 RST 버튼으로만 풀렸다(설정값은 정상
상태와 동일했다).

- **REBOOT 는 원인도 해결책도 아니다**: 이상 상태를 풀지 못했고, 정상 상태에서 보내도 나빠지지 않았다. USB 끊김
  대비라는 원래 목적은 그대로라 시작 시 리셋은 유지한다.
- **소프트웨어 전원 차단은 Pi 5 본체 포트로 불가**:
  - 허브가 `ppps` 를 보고하지만, `usb2-port2/disable` 로 장치를 떼어도 VBUS 가 남아 보드 LED 가 꺼지지 않는다.
  - `uhubctl` cycle 은 커널이 1 s 안에 다시 켠다.
- **당분간 수동**: 증상이 보이면 전원을 완전히 내렸다 올리거나 RST 버튼을 누른다. 계기를 모르니 예방 주기도 정할 수 없다.

## 마이크 입력을 CH1(ASR 출력) + 고정 게인 한 채널로 (2026-10-14)

호출어 감지와 노래 재생 중에도 같은 채널을 쓴다.

- **CH0 을 버린 이유**:
  - CH0(Conference)은 AEC 뒤 후처리(에코 잔여 억제·잡음 억제·AGC)를 거친다. 더블토크 때 이 억제가 근단까지 눌러,
    끼어든 말이 한 음절로 잘렸다. AEC 이상 상태에서 특히 심했다.
  - CH1 은 XMOS 문서상 빔포머 뒤에서 바로 꺼내 후처리를 거치지 않는다.
  - 녹음을 귀로 비교했을 때 CH1 이 훨씬 나았다.
- **작은 에코는 받아들인다**:
  - CH1 에는 선형 AEC 잔여가 조금 남는다. cascade 의 Google ASR 은 이 잔여 때문에 전사가 깨져 못 쓰던 채널이다.
    반면 GPT-Live 는 잘린 말보다 약간의 에코를 훨씬 잘 견딘다.
  - 단 AEC 이상 상태에서는 CH1 로 에코가 크게 샌다(−55 dBFS). 그러면 모델이 자기 말에 반응할 수 있는데, 그 상태는
    수동 전원 재투입으로 대응한다.
- **호출어 감지도 CH1**:
  - SLEEP 에는 로봇 발화가 없어 더블토크와 무관하다. 그래도 채널을 모드별로 나누는 복잡도는 들이지 않는다.
  - CH0 의 AGC(최대 +30 dB)가 없어 멀리서 부르는 소리는 덜 잡힌다. 가까이 와서 부르는 사용을 전제로 받아들였다.
    AGC 가 없으면 거리 정보가 남아 먼 TV·대화 소리가 작게 들어가는 이점도 있다.
  - 집에 고정해 두고 멀리서 부르는 사용이 필요해지면 재검토한다. 후보는 호출어만 CH0 을 쓰거나, CH0 + `PP_AGCMAXGAIN` 하향이다.
- **게인 +20 dB**: CH1 은 같은 말소리가 CH0 보다 ~25 dB 작다. 이날 녹음 14 개의 CH1 피크는 대부분 −25 ~ −38 dBFS 라
  +20 dB 에서도 여유가 5 dB 이상 남는다. 넘는 것은 기기를 건드린 순간 같은 짧은 과도음뿐이다.
- **cascade 도 CH1 을 받는다**: 기본 엔진이 live 라 당장은 무관하다. cascade 를 다시 쓰면 채널을 엔진별로 나눠야 한다.
- **노래 재생 중 원본 채널 전환도 없앤다**:
  - 원본 CH2 로 바꾸던 이유는 음악 재생 중 CH0 이 후처리 게이트로 막혀서였다([노래 재생 기록](songs-led.md)).
  - CH1 은 후처리를 거치지 않아 막히지 않는다. 노래 녹음(14.9 s)에서 CH0 은 재생 내내 −54 dBFS 평탄했고,
    CH1 은 −42 ~ −57 dBFS 로 움직였다.
  - 음악 잔여는 CH1 에도 남는다. 다만 원본 CH2 는 음악이 그대로 섞인 채로도 GPT-Live 가 사용자 말을 구분했다.
  - 채널이 하나면 루프가 마이크를 건드릴 일이 없다. 그래서 채널 전환 코드와 `LiveSessionLoop` 의 `audio_input` 의존이
    통째로 빠진다.

## 기록 당시 남은 문제

- **잡음 억제 없음**: CH1 에는 팬·에어컨 같은 정상 소음이 그대로 들어간다. 실사용 환경에서 확인할 것.
- **AEC 이상 상태의 계기 미상**: 수동 전원 재투입으로만 대응한다. 하드웨어 리셋 자동화(Pi GPIO → 보드 RST)는
  [decisions-wip.md 의 차후 고려](../decisions-wip.md#차후-고려)에서 관리한다.
