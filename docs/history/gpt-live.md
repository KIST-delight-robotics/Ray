# GPT-Live 엔진 전환

> 2026-09 ~ 2026-10 GPT-Live 엔진 전환 작업의 기록. 완료 후 고정 — 이후 변경은 반영하지 않는다.

## 개요

턴테이킹·ASR·LLM·TTS 체인(cascade)을 OpenAI GPT-Live full-duplex 모델 하나로 바꾼 작업이다. 엔진은 2026-09-16
들어왔고 `settings.ENGINE` 으로 cascade 와 공존했다. 엔진 구조(연속 스트림, 지연 보정, 위임 백엔드 툴, 종료 경로)를
정한 뒤, "같은 소리로 모션을 만드니 싱크가 맞는다" 는 설명을 실측으로 확인했다(09-17). 이어서 볼륨·밝기 음성 제어를
백엔드 툴로 붙였다(09-21). 바뀐 출력 레벨에 맞춰 입 모션 입력과 재생 파일(차임·인사) 레벨도 정규화했다(09-28).
API 동작 실측은 [FINDINGS.md](../../scripts/gpt_live/FINDINGS.md)에 있고, 여기에는 그중 설계를 가른 판단만 둔다.

## 스트림과 지연 보정

- **대화 구간은 연속 스트림**: live 는 무음도 실시간으로 온다. 발화마다 끊으면 클라이언트가 발화 끝을 추정해야 하고,
  이전 재생이 끝나기 전에 `stream_start` 가 버퍼를 비우는 위험도 생긴다. 그래서 무음까지 하나의 스트림으로 보낸다.
  노래를 재생할 때만 `audio_end` → `playback_complete` 뒤 파일로 교대하고, 끝나면 스트림을 다시 연다.
- **헤드모션은 live 스트림에서도 오디오로 생성**: 무음까지 한 스트림이라 듣는 동안에도 생성 경로를 타지만 움직임이
  멎지 않는다.
  - 무음 덩이는 가장 작은 클래스(`segment_0`)에 무성 감쇠가 걸린다. 그런데 감쇠 카운터가 360 ms 덩이마다
    초기화되고 바닥이 0.3 이라 원 움직임의 40~80% 가 남는다.
  - C++ 경로를 Python 으로 옮긴 시뮬레이션에서 무음 구간은 대기 모션(×3.0) 대비 속도 약 0.7배, 3초 이동폭 약
    0.6배였다. 무음 1시간에도 위치 편향·후보 부족이 없었다.
  - live 전용 처리(채움·버림·프리버퍼·되돌리기)는 모두 split 앞이라, 모션 생성은 보통 스트림과 같은 입력을 받는다.
- **프리버퍼는 C++ 한곳에서**: 실시간 데이터가 도착하자마자 모션 시계를 시작하면 매 덩이마다 기다렸다가 모터 틱을
  몰아친다. 그래서 소비 기한을 아는 C++ 에서 시작 여유를 모으고, 파이썬에는 별도 프리버퍼를 두지 않는다.
  초기 두 덩이만으로는 지터 때 재생기 큐가 비어, 원시 버퍼에 추가 여유를 남기는 방식으로 보완했다. 여유는 응답
  지연과 맞바꾸는 값이다. 실험 조건·수치는 [FINDINGS §2](../../scripts/gpt_live/FINDINGS.md#2-오디오-출력-특성).
- **서버 유실은 파이썬, 전송 정지는 C++ 에서 보정**: "지연 누적 방지를 넣지 않는다" 는 초기 판단은 서버 무음 유실과
  재생기 언더런을 실측한 뒤 폐기했다.
  - 파이썬은 보낸 양과 경과 시간의 차이를 무음에서 보정한다.
  - 전송이 멈추면 새 조각이 없어 이 보정이 실행되지 않는다. 그래서 C++ 는 소비 기한 + 유예까지 기다린 뒤
    `stream_and_split` 에서 부족분을 채워 재생·분석 큐에 같은 덩이를 넘긴다.
  - 재생기만 무음을 넣으면 소리만 밀리고 모션은 따라잡아 싱크 오차가 누적되기 때문이다.
- **채운 지연은 C++ 에서 무음으로 되돌림**: 원시 버퍼에 실제로 남은 잉여 무음만, C++ 가 채운 누계까지 버려 여유를
  복구한다. 말소리에는 손대지 않지만 문장 사이 쉼이 짧아지는 비용은 있다.
  - 파이썬 타이머로 채우는 안은 C++ 가 흡수할 정지에도 구멍을 내므로 기각했다.
  - C++ 채움량을 파이썬에 보고하는 별도 회계도 두지 않았다. C++ 안에서 채움과 되돌리기가 상쇄되기 때문이다.

## 위임·종료·주입

- **responses 위임 + 함수 툴**: 대화 모델은 툴을 직접 갖지 못하고 "백엔드에 넘길지" 만 판단한다.
  - client 위임은 위임 이벤트에 요청 텍스트가 없어 전사로 재구성해야 한다.
  - responses 위임은 백엔드가 대화 이력 전체(전사 그대로, 모델 발화 포함)를 자동으로 받는다. 60초 침묵 뒤에도 앞
    턴을 참조함을 확인했다.
  - 레이 고유 기능은 백엔드의 function 툴로 붙인다(`response.output_item.done` → 실행 → `response.item.create` →
    `response.create`, 배터리 예제 2.2초).
- **위임 판단은 프롬프트 형식에 좌우**: 규칙을 덧붙여 쓴 프롬프트는 작별 위임 3/5, MUST 로 강화하면 0/3, 공식
  템플릿 구조(Backend tools / Delegate when / Do not delegate when)는 7/9 였다. 그래서 지시문은 템플릿을 그대로
  따르고 덧붙이지 않는다.
- **종료는 다층**: `end_conversation` 툴은 자연스럽지만(모델이 인사하는 동안 병행 호출, 대기 없음) 모델 재량이라
  누락이 있다.
  - 기본은 사용자 전사 키워드 + 유휴 타임아웃이고, 툴은 빠른 경로다. "안녕" 은 인사와 겹쳐 키워드에서 뺐다.
  - 종료 시퀀스: `input_audio.mute`(ack 0.24초, 세션은 멈추지 않음) → 출력 무음 1초(당시 상한 8초) →
    `session.close` → 브리지 `audio_end`. (→ 이후 노래 재생 작업에서 상한을 30 s 로 올림 —
    [노래 재생·LED](songs-led.md)의 "대기 상한" 항목)
  - 툴 뒤 `response.create` 로 이어가면 백엔드가 작별을 또 만들어 모델이 두 번 말할 수 있다(2/4). 그래서 이어가지
    않는데, 그러면 `session.closed` 가 9.4초 뒤에 온다. 과금은 요청 시점에 멈추고 오류도 없어 기다리지 않고
    `playback_complete` 만 기다린다.
  - 작별 WAV 는 모델이 인사하므로 생략한다. 인사 WAV 는 연결 지연(1.5~3.5초)을 가리는 용도로 유지한다.
- **세션 중 주입 규칙**: `instructions.append` 는 내용과 무관하게 진행 중 발화를 끊는다(6회 중 5회) — 모델이 조용할
  때만 쓴다. `thinking.append` 는 발화를 유지하며 반영되고, 언어 전환까지 문장 중간에서 된다(4/4). 어느 쪽이든
  모델이 주입 사실을 소리 내어 말할 수 있고 "조용히 적용" 문구로 막지 못한다 — 새어 나가도 되는 표현으로 넣는다.
- **전사는 모델의 귀**: 별도 인식기라는 말이 문서·레퍼런스 어디에도 없고, 오인식 때 전사와 모델 반응이 같은 방식으로
  틀린다. 그래서 전사로 오인식을 검출할 수 없고, 틀린 전사가 그대로 기억에 저장된다. SDK `TranscriptGrouper` 로
  화자별 세그먼트를 묶으면 실제 세션에서 턴이 깨끗이 나뉜다.
- **컨텍스트 창은 작다**: 128k 중 무음도 초당 약 20토큰, 발화 중 약 48토큰을 먹어, 보통 대화 50분쯤에 90% 교체(원본
  instructions + 8,192 토큰 요약)가 온다. 장기 사실은 우리가 갖고 있다가 다시 넣는다는 전제다. 세션 만료는
  `expires_at` 기준 120분.
- **SLEEP 은 로컬 유지**: "말 걸 때만 답하라" 지시로도 주변 대화에 끼어든다. 침묵은 마이크 mute 나 세션 종료로만
  보장되고 세션 유지 비용($3/시간)도 있어, 웨이크워드는 지금처럼 로컬에 둔다.

## 오디오·모션 싱크 실측

2026-09-17. 구조적 설명만으로는 부족해 실측했다.

**측정 방법**: 도구는 `scripts/bench/live_sync_probe.py` 이다. 실제 `LiveSessionLoop`·`CppBridge` 를 쓰고
GPTLiveSession 자리만 가짜(합성 톤 버스트를 실시간 페이싱)로 바꿔, Python 채움·버림과 C++ 프리버퍼·split 채움 경로를
그대로 타게 했다. 스피커 출력(reSpeaker 원본 마이크 채널)과 입 모터 실제 위치(Standard_Log `Present_Pos_4`)를 C++
`start_time` 축(`playback_started` 수신 시각)으로 맞춰 창 단위 상호상관으로 비교한다.

- **싱크가 어긋날 수 있는 지점은 분기 뒤 두 소비자뿐**: `stream_and_split` 이 덩이 하나를 재생기와 모션 분석기에
  똑같이 넘긴다. 그 앞의 처리(Python lead 채움·버림, 프리버퍼, split 유예 채움, trim-back)는 무엇을 넣고 빼든 두
  스트림에 똑같이 들어가 싱크를 깨지 못한다. 네트워크 정지·서버 프레임 유실도 지연만 바꾼다. 싱크를 깨는 경로는 둘이다.
  1. 재생기만 무음을 끼우는 언더런 폴백. Live 도입 초기(09-15) 관측된 밀림은 전부 이것이었다 — 계단 높이가 끼운
     무음과 정확히 일치했다. split 유예 채움(기한 + 450 ms 에 0 을 채워 양쪽에 넘김)이 이 경로를 닫아 이후 세션은
     언더런 0 ms. 남는 발동 조건은 네트워크가 아니라 split 스레드 자체가 약 390 ms 이상 늦는 CPU 경합이다.
  2. 재생기(DAC 시계)와 모터(steady clock)의 시계 속도 차.
- **물리 오프셋 약 +10 ms (입이 소리보다 늦음)**: 스트림 위치 기준 마이크 도달 +59 ms(출력 지연 + 마이크 입력 지연),
  입 목표 −27 ms(`future_frames` 미리보기), 모터 기계 지연(목표→실제) +96 ms → 입 실제 ≈ +69, 차이 ≈ +10 ms.
  마이크 입력 지연이 포함된 값이라 실제는 0 에 더 가깝다. 30초 창 사이 흔들림 ±4 ms, 상관 0.7~0.9.
- **드리프트는 실제이고 하드웨어 특성**: XVF3800 클럭이 Pi monotonic 보다 54.5 ppm 느리다(캡처 read 시각 대 누적
  샘플 선형 적합). audio_sync CSV 의 `expected − (playing − silence)` 기울기 3.3 ms/min 과 일치한다. 세션 = 스트림
  하나인 live 에서 1시간이면 소리가 입보다 약 200 ms 뒤처진다. 보정은 적용하지 않았다(아래 남은 문제).
- **마이크로는 이 드리프트를 볼 수 없다**: reSpeaker 의 ADC 와 DAC 가 한 클럭이라 녹음 시간축이 재생과 같이 늘어나
  상쇄된다. 물리 측정 기울기 0.00 ms/min 이 그 증거다. 드리프트는 클럭 비율 측정이나 다른 장치(휴대폰 영상)로만
  확인할 수 있다.
- **측정 신호 설계**: 1 s 주기·150 ms 버스트는 입 반응 크기가 버스트마다 21~92 DXL 로 달라 온셋 매칭이 잡음에
  묻혔다. 버스트가 360 ms 덩이 경계의 어느 위치에 떨어지느냐에 따라 SG 피크 알고리즘 출력이 달라지기 때문이다.
  주기를 덩이 4개(1.44 s)로 맞추고 300 ms 버스트로 바꾸고, 마이크는 톤 주파수(220/440/660 Hz) 성분만 추적해 모터
  소음을 배제하니 상관이 0.4 → 0.7 이상으로 올랐다. Ray 는 프로세스당 Standard_Log 하나에 세션을 이어 쓰므로
  마지막 RESPONSES 구간만 고른다.
- **Wi-Fi 전송 정지**: 09-17 실동작에서 발화 중 1.0~1.6 s 전송 정지가 연속으로 와(버퍼 흡수 한계 약 850 ms 초과)
  split 채움 4.7 s 로 끊김이 들렸다. 정지 뒤 원시 버퍼가 1.3 s 까지 불어난 것으로 보아, 서버 생성 정지가 아니라 전송
  경로 정지다. 다만 어느 구간(Wi-Fi 홉/상위 망)인지는 로그로 갈리지 않는다.
  - 간헐적이라 `scripts/hardware/net_probe.py` 를 만들었다. 게이트웨이·외부 호스트에 200 ms 간격 ping(비root 최소값;
    1 s 정지가 5개 연속 이상으로 찍힘)을 RTT 와 함께 기록하고, 파이프라인 `Audio chunk gap` 과 대조한다.
  - 손실보다 "큐에 갇혀 늦게 도착" 이 많아 RTT ≥ 300 ms 도 이상으로 본다.

## 볼륨·밝기 음성 제어

2026-09-21.

- **경로는 백엔드 함수 툴 하나뿐**: 대화 모델은 툴을 직접 갖지 못하고 responses 위임 백엔드만 함수를 부른다
  (`search_memory` 와 같은 길). 위임 → 툴 → 발화가 약 2초라 "올려줘" 뒤 2초쯤에 확인 멘트가 나온다. 전사 키워드
  매칭으로 앞당기는 안은 오인식·표현 다양성 때문에 두지 않았다.
- **스마트 스피커처럼 단순하게**:
  - 볼륨은 `adjust_volume(direction, steps)` 올리기/내리기만 있고 끄기는 없다(최소 10%). 퍼센트를 직접 받으면
    "조금 올려줘" 해석이 모델마다 흔들리고, 한 칸씩만 받으면 "최대로" 가 여러 번 위임되어 느리다 — 단계 + 칸수
    (보통 1, "많이" 2)로 절충했다.
  - 칸이 모자라면 실패가 아니라 가능한 만큼 움직이고 `at_limit` 를 돌려줘, 백엔드가 "최대예요/최소예요" 라고 말한다.
  - 밝기는 `set_brightness(level)` 단계 이름 하나(off/low/medium/high).
  - 현재 상태는 `get_device_settings()` 로 따로 조회한다. 백엔드 지시문은 세션 중 갱신하지 않으므로 상태를
    프롬프트에 박을 수 없다.
  - "더 밝게" 같은 상대 표현: 백엔드가 이력 전체를 받으므로, 같은 세션의 앞 툴 결과에서 현재 단계를 알면 바로 옆
    단계로 간다. 모를 때(세션 첫 요청, 재부팅 뒤)만 조회를 먼저 한다. 항상 조회하게 하면 위임마다 툴을 두 번 불러
    약 1초가 늘어서 그렇게 두지 않았다.
- **볼륨은 PipeWire 싱크(wpctl)**: C++ 에 메시지를 추가하는 대신 `wpctl set-volume @DEFAULT_AUDIO_SINK@` 를 쓴다.
  - C++ 변경이 없고, 인사 WAV·차임도 같이 조절되고, 핸들러가 executor 스레드에서 돌아도 CppBridge 의 스레드
    규칙(오케스트레이터 전용)을 건드리지 않는다.
  - 입 모션은 볼륨 적용 전 PCM 이고 AEC 참조는 PipeWire 뒤 USB 라 영향이 없다.
  - 두 서비스가 `systemd --user` 아래라 서비스 환경에서도 wpctl 이 붙는다.
  - 기본 싱크가 흔들리는 기기가 나오면 C++ `sf::SoundStream::setVolume` 경로로 바꿀 수 있게 `set_volume` 을
    주입점으로 뒀다.
- **밝기는 드라이버 계수**: `LEDController.set_brightness()` 가 rpi5_ws2812 의 밝기 계수를 바꾼다. 드라이버가
  `show()` 마다 곱하므로 애니메이션·상태는 그대로 두고 다음 프레임부터 어두워진다. 하부 PWM LED 미러는 프레임
  원색으로 duty 를 내던 것이라 같은 계수를 곱해 따라오게 했다. 밝기 0 과 `LEDState.OFF` 는 다른 개념이다.
- **저장은 `var/device_settings.json`, 시작 시 재적용**: 프로그램이 쓰는 값이라 `config/` 가 아닌 `var/` 에 둔다.
  단계 이름으로 저장해 퍼센트 표를 바꿔도 의미가 유지된다. 기본값은 도입 전 동작(볼륨 100%, 밝기 1.0)과 같게 둬
  배포 시 소리·밝기가 갑자기 바뀌지 않는다. 볼륨 재적용 실패(PipeWire 미기동, 개발 PC)는 경고만 한다.
- **툴 노출은 핸들러 기준**: wiring 이 핸들러가 등록된 툴만 백엔드에 준다. 기존의 "메모리가 꺼지면 search_memory
  제외" 분기도 이 규칙 하나로 흡수됐다.

## 입 모션용 오디오 레벨 정규화

2026-09-28. GPT-Live 로 바꾼 뒤 입이 작아졌다.

- **원인은 다이나믹이 아니라 절대 레벨**: 저장된 WAV 로 재 보니 40 ms 피크 중앙값이 ElevenLabs ≈0.45, OpenAI TTS
  ≈0.33, GPT-Live ≈0.17 이었다(RMS 는 각각 0.21 / 0.09 / 0.07). 상대 다이나믹(p90/중앙값)은 GPT-Live 가 오히려
  크다. PART B 는 진폭 ×`min_mouth` 가 기본이고, 피크 보정은 문턱(0.18)을 넘는 볼록 피크만 0.52 로 올린다. 그래서
  유성 프레임의 절반 가까이가 문턱 아래인 GPT-Live 에서는 바탕이 그대로 작게 남는다.
- **고정 gain 은 벤더·목소리마다 다시 틀어진다**: `MOUTH_AUDIO_GAIN` 이 3월에 3 → 1.0 으로 오간 이력이 그 증거다.
  live 스트림만 2.5 로 키워 가설을 확인한 뒤(체감 일치), 스트림 안에서 "최근 최대 피크" 를 추적해 0.8 에 맞추는
  배율 하나를 곱하는 방식(`MouthLevelNormalizer`)으로 바꿨다. (→ 이후 목표 피크 0.7 로 하향, 2026-09-29 커밋
  b3d65ba)
  - 배율이 하나라 음절 간 다이나믹은 보존된다. 프레임마다 다른 배율을 곱하는 컴프레서류는 입이 계속 벌어져 동작이
    사라지므로 피했다.
- **추적은 유성 프레임에서만**:
  - 40 ms 피크 < 0.02(≈-34 dBFS)는 갱신도 감쇠도 하지 않는다. 노이즈·숨소리가 최대치로 잡히지 않고, Live 세션처럼
    발화 사이 무음이 길어도 이전 발화의 배율이 유지돼 다음 발화 첫 음절이 바로 맞는다.
  - 시작 시 추적값은 비워 두고 첫 유성 프레임(미리 보기 360 ms 포함)으로 초기화한다. 기본값에서 수 초에 걸쳐
    내려오는 방식은 첫 문장이 통째로 작아 최악이다.
  - 배율 범위 [1, 5]: 하한 1 은 이미 큰 소리(ElevenLabs)를 지금과 같게, 상한 5 는 무음 구간이 부풀지 않게.
    사전 시뮬레이션에서 GPT-Live 가 ElevenLabs 분포와 거의 겹치고 클리핑 0% 였다.
- **재생 소리에는 적용하지 않는다**: 소리 크기는 시스템 볼륨(`adjust_volume`)이 정하는 값이라 AGC 가 끼면 두 제어가
  싸우고, 펌핑·클리핑이 귀에 들리며, 스피커가 커지면 reSpeaker 더블토크 억제가 나빠진다. `stream_and_split` 이
  재생용 int16 과 모션용 float 를 이미 따로 만들어 두어 모션용만 손대면 된다.
  - 참고로 볼륨은 XVF3800 하드웨어 볼륨으로 적용된다(PipeWire softVolumes 는 1.0 유지, 장치 `PCM Playback Volume`
    만 변함). 그래서 USB 로 가는 PCM 과 AEC 참조는 볼륨과 무관하게 항상 같은 레벨이다.

## 재생 파일 출력 레벨 정규화

2026-09-28. 차임과 인사/작별 WAV 가 대화 음성보다 확연히 컸다. 측정해 보니 인사 WAV 는 GPT-Live 출력보다 약
+8.8 dB, 차임은 피크가 0 dBFS 를 찍어 클리핑까지 났다. 세 소리가 한 스피커에서 번갈아 나는데 레벨 기준이 없었던 것이다.

- **기준은 GPT-Live 말소리**: 대화 시간의 대부분이 그 소리다. 그리고 라이브 출력 레벨은 벤더가 정해 우리가 못
  바꾼다 — 맞출 수 있는 쪽은 항상 파일이다. 인사 WAV 를 기준으로 삼으면 안 되는 이유이기도 한데, ENGINE=live 에서도
  인사는 Realtime 출력이 아니라 별도 `OpenAITTS` 로 만든 캐시라 레벨 계통이 다르다.
- **척도는 LUFS 가 아니라 "유성 40ms 프레임 피크"**: 실시간 스트림은 턴마다 무음 비율이 달라 통합 LUFS 가 콘텐츠가
  아니라 침묵을 잰다 — 같은 4개 세션 실측에서 LUFS 편차 4.7 dB, 이 척도 3.4 dB. 게다가 cpp `MouthLevelNormalizer`
  가 이미 같은 척도(40ms 피크, `kVoicedPeak=0.02`)를 런타임에 추적해 `[mouth] gain` 로그로 실기 대조가 된다. 새
  척도를 들이는 것보다 있는 것에 붙이는 게 낫다.
- **대표값이 소리 종류마다 다르다**: 말소리는 중앙값(발화가 앉아 있는 높이), 알림음은 p90 을 쓴다. 차임은 어택이 크고
  감쇠 꼬리가 길어 중앙값이 체감을 과소평가한다 — `ready.oga` 실측 중앙값 0.157 / p90 0.456.
  - 목표는 말소리 0.12(GPT-Live 실측), 알림음 p90 0.11 이다. 알림음은 의미를 나르지 않아 같은 크기면 시끄러우므로
    말소리 p90 보다 ~8 dB 아래로 잡았다.
  - 처음 잡은 0.15(5 dB 아래)는 실기에서 말소리보다 크게 들렸다. 아래 "두 경로 게인 1:1" 가정이 깨졌을
    가능성(OpenAL 의 mono → 스테레오 분배)도 있으나, 확인하지 못해 귀로 낮췄다.
- **재생 순간이 아니라 정규화 사본으로**: 차임은 `pw-play`, 인사는 C++ `play_file` 로 경로가 갈린다.
  - 출력단(`read_and_split` 의 int16 변환 지점)에 gain 을 넣는 안이 더 "출력단"답지만, 차임이 그 경로를 안 지나가
    결국 장치가 둘로 갈리고 C++·브리지 프로토콜까지 건드려야 한다.
  - `var/audio/normalized/` 에 사본을 쓰고 그 경로를 재생하면 두 경로가 한 장치를 쓰고 Python 안에서 끝난다. 원본
    자산도 그대로다.
  - `pw-play --volume` 을 안 쓴 이유도 같다 — 볼륨 커브가 선형인지 확인이 필요한데, 사본이면 그럴 일이 없다.
- **WAV 전용으로 좁히지 않는다**: 차임이 Ogg 라 stdlib `wave` 로 못 읽어 `soundfile` 을 코어 의존성으로 올렸다.
  "무슨 파일을 넣든 맞춰준다" 가 이 기능의 요구였고, WAV 전용은 그걸 깬다.
- **정규화 뒤 재측정은 목표보다 0.6 dB 쯤 높게 나온다**: `VOICED_PEAK_FLOOR` 가 절대값이라, 감쇠 후에는 작은
  프레임이 더 잘려 분포가 위로 밀린다. 되먹임으로 수렴시킬 만한 크기가 아니라 문서로만 남긴다.

## 기록 당시 남은 문제

- **헤드모션 크기**: 클래스 경계값(raw RMS)이 TTS 레벨 기준이라, live 출력에서 말소리 움직임 크기가 맞는지는 실기로
  봐야 한다. 듣는 동안 움직임이 부족하면 무성 감쇠 바닥을 설정으로 빼 올린다(감쇠 없이 `segment_0` ≈ 대기 모션 크기).
- **전사 세그먼트 경계**: 사용자 세그먼트는 시간 경과로 닫히지 않고 모델이 말할 때 닫혀, 긴 침묵 앞의 잡음이 다음
  요청에 붙을 수 있다(후처리 후보).
- **재생 드리프트 보정**: 미적용. [decisions-wip.md 의 차후 고려](../decisions-wip.md#차후-고려)에서 관리한다.
- **Wi-Fi 전송 정지 구간**: Wi-Fi 홉인지 상위 망인지 미판별. `net_probe.py` 를 세션 옆에 켜 두고 다음 정지를 기다리는
  상태였다.
- **볼륨·밝기 미검증**: 실기에서 백엔드가 "많이" 를 steps=2 로 옮기는 비율, 밝기 단계 값(0.3/0.65)의 체감, 위임 누락률.
- **재생 파일 레벨 미검증**: 파일 레벨 비교라 `pw-play` → PipeWire 와 C++ → OpenAL → PipeWire 두 경로의 게인이 1:1
  이라는 가정 위에 있다. 어긋나면 차임과 인사의 상대 크기가 계산과 달라진다 — 실기에서 마이크로 같은 세션에 녹음해
  대조할 것.
