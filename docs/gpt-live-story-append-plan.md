# GPT-Live 이야기 대본 직접 주입 계획

상태: 기존 실행 경로에 직접 주입 연결. responses 위임과 gpt-5.4-mini 백엔드를 유지한다.

## 적용 상태

- 대본 10개의 도입부 응답 질문을 서술로 변경했다. 본문과 마지막 노래 제안은 유지한다.
- start_story는 준비 지시와 대본의 append 수락 후 prepared 메타데이터만 반환한다(교체는 finish_story 뒤 start_story).
  기존 툴 결과 제출을 거쳐 같은 위임의 최종 성공 응답을 확인하면 commentary 시작 신호를 보낸다.
- 백엔드는 대본을 생성하지 않고, 대화 모델은 주입된 텍스트로 진행·재개·재청취한다.
- 전송 오류·시간 초과·취소는 성공으로 처리하지 않는다. 전송별 ID로 늦은 이벤트를 구분한다.
- 확인 필요: 이전 별도 실험 1회에서 마지막 노래 제안까지 발화했지만, 시작 신호 전 조기 발화와
  도입부 한 문장 누락이 있었다. 준비 지시를 수정했으며 해결 여부는 사용자의 실제 음성 테스트로 확인한다.
- 기존 실행 방식으로 테스트한다. 별도 실세션 자동 실험은 추가 실행하지 않았다.


## 목적

이야기 검색·선택과 툴 판단은 백엔드가 맡고, 선택된 대본은 애플리케이션이 GPT-Live에 직접 전달한다.
백엔드가 대본을 다시 생성하는 과정과 도입부 답변 후 본문을 받기 위한 추가 위임을 없앤다.
사용자 질문·끼어들기·재개 동의, 노래 재생 동의 및 자연 종료 후 감상 대화는 유지한다.

## 먼저 확인할 실험

운영 흐름을 바꾸기 전에 실제 GPT-Live 세션으로 대본 직접 주입을 시험한다.
텍스트 Responses 모델 호출만으로는 이 방식의 성공을 검증할 수 없다.

- 현재 responses 모드를 유지하고 저장된 대본을 thinking.append로 나눠 전달한다.
- 각 이벤트에는 고유 event_id를 쓰고 appended의 client_event_id로 수락을 추적한다.
- content 전체를 토큰 계산하며, 번호·이야기 ID·설명까지 포함해 각 450토큰 이하를 목표로 한다.
  문장 경계로 분할한다. 조각은 전송 단위일 뿐 발화 대기 지점이 아니다.
- 준비 지시 → 조각별 수락 → 짧은 백엔드 작업 완료 → 시작 신호 한 번의 순서를 검증한다.
- 시작은 우선 commentary.append로 유도한다. 모델이 안내 문구를 읽거나 대본을 활용하지 못하면
  짧은 instructions.append 시작 지시와 비교한다. 시작 전이므로 진행 중 발화를 끊지 않게 한다.
- appended는 주입 수락을 나타내며 내용 전체 활용·발화 완료의 증거가 아니다.
  실제 출력 오디오와 전사를 대본과 대조한다.
- 스피커·실제 장치 동작 없이 오디오를 저장하는 실험을 우선한다. 음성 입력은 합성 사용자 발화와
  실시간 속도의 무음 PCM으로 공급한다. 내부 세션 시계가 흐르도록 오디오 송신을 유지한다.

## 구현 순서

1. 대본 준비
   - 도입부와 본문을 합친 발화 텍스트를 추출한다. 곡 프로필·제목·진행 메모는 발화 텍스트에서 제외한다.
   - 도입부의 답변 유도 질문은 대본 파일에서 자연스러운 서술로 바꾼다. 마지막 노래 제안은 유지한다.
   - 원문 사실과 순서를 보존하고 문장 경계에서 450토큰 이하로 나눈다.

2. 어댑터 이벤트
   - thinking/instructions/commentary append에 event_id 지정 및 수락·오류 추적을 추가한다.
   - Responses의 delegation_id와 response_id, 완료 상태를 연결해 기록한다.
   - 함수 호출을 반환한 response.completed와 툴 결과 처리 후 끝난 최종 응답을 구분한다.
   - 프레임 루프를 막지 않고 이벤트와 타이머로 기다린다.

3. 이야기 시작·교체
   - 기존 무음 대기 뒤 준비 지시를 적용한다. 준비 중에는 대본 발화를 시작하지 않도록 한다.
   - 선택된 이야기의 조각들을 순서대로 주입하고 수락을 확인한다.
   - start_story 결과에는 ID·상태 등 짧은 메타데이터만 준다. first_part 본문 전달은 없앤다.
   - 같은 위임을 처리하는 기본/이야기 백엔드 모두 성공 후 대본을 생성하지 않고 빈 최종 응답으로 끝내도록 한다.
     짧은 완료 문구가 발화 시작 신호와 겹치지 않게 하기 위한 초기 선택이다.
   - 해당 위임의 최종 완료를 확인한 뒤 시작 신호를 한 번 보낸다.
   - 준비 지시/대본 주입 실패나 시간 초과는 성공으로 보고하지 않는다. 보류 중 Future도 반드시 정리한다.

4. 기존 규칙 정리
   - 대화 모델은 처음부터 마지막 노래 제안까지 자연스럽게 전달한다. 도입부 답변 대기는 없앤다.
   - 짧은 맞장구에는 이어가고, 질문·곁 대화에는 멈춰 답한 뒤 재개 동의를 받는다.
   - 재개·다시 듣기는 이미 받은 대본을 사용한다. 정상 진행에서 다음 본문을 받기 위한 위임은 없앤다.
   - 백엔드는 검색·교체·종료·노래·장치·기억·사실 확인을 맡는다. 이야기 전문을 생성하는 규칙은 제거한다.
     대본을 질문 답변용 참고로 백엔드에 유지하는 것은 가능하다.
   - 노래 제안의 동의와 자연 종료 후 일반 모드 감상 질문은 유지한다.

5. 취소·교체 보호
   - 주입 작업마다 이야기 ID와 세대 번호를 둔다. 뒤늦은 ack나 백엔드 결과가 이전 이야기 시작을 유발하지 않게 한다.
   - 준비 중 취소/교체/종료가 들어오면 아직 보내지 않은 조각과 시작 신호를 폐기한다.
   - 이미 주입한 텍스트는 삭제할 수 있다고 가정하지 않는다. 현재 유효한 이야기와 취소 상태를 명확히 전달한다.

## 검증과 판단 기준

- 단위 테스트: 토큰 제한과 원문 복원, 메모 제외, ack 매칭, 최종 응답 판별, 오류·시간 초과·취소·늦은 이벤트.
- 실세션: 무개입 완주 3회, 짧은 맞장구, 질문 후 재개, 다시 듣기, 교체, 준비 중 취소, 노래 동의/거절.
- 확인: 주입 준비 중 조기 발화가 없는지, 첫/마지막 내용과 주요 사실의 보존, 전송 조각 경계에서 멈추지 않는지,
  중복·요약·누락·불필요한 위임이 없는지. 전사만으로 불명확하면 녹음을 듣는다.
- 지연은 시작 툴 수신→각 append 수락→백엔드 최종 완료→첫 실제 이야기 음성으로 나눠 기록한다.
  백엔드 토큰 생성 시간과 사용자 체감 시작 지연을 구분한다.
- 전체 대본 직접 전달의 실행 가능성을 먼저 확인한다. 실패하면 운영 경로에 적용하기 전에 원인과 대안을 검토한다.
