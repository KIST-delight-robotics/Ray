# 이야기 모드

> 사용하지 않는 이야기 모드(`search_stories` / `start_story` / `finish_story`)의 기록. 고정 — 이후 변경은 반영하지 않는다.

## 개요

GPT-Live 엔진에서 저장된 노래마다 어울리는 이야기를 3~5분 들려준 뒤 노래를 트는 콘텐츠. 2026-09-28 에 넣고, 이튿날
대본을 대화 모델에 직접 넣는 방식으로 바꿨다가, 레이의 방향성과 맞지 않아 2026-10-01 코드·대본·툴을 전부 제거했다
(DJ → 라디오 모드로 대체, [history/2026-10-radio/](../history/2026-10-radio/)). 제거 전 코드는 커밋 9acab27 까지의
`engines/gpt_live/stories.py` · `story_append.py` 에 있다.

기능 설명이 아니라 교훈으로 남긴다 — `instructions.append` 는 발화를 끊으니 출력 무음 뒤에만, `session.update` 는 다음
위임부터 적용, 시작 허가 전 조기 발화, 자연 종료를 아무도 알리지 않는 문제.


## 기획

박사님 요청: 저장된 노래마다 어울리는 이야기를 3~5분 들려준 뒤 노래를 트는 콘텐츠. "라디오" 는 아니고, ACTIVE 세션
안에서 사용자와 주고받으며 진행. 대본은 `assets/song_stories/<곡키>.md` (2026-09-28 기준 10곡).

- **이야기가 주(主), 노래는 끝에 딸림**: 사용자는 "이야기 해줘" 라고 하고 레이가 이야기를 고른다. 곡을 정해 놓고 그 곡
  설명을 하는 게 아니라, 곡의 정서·소재에 맞는 독립된 이야기(유명한 일화·작품·사실)를 하고 브릿지에서 처음 노래를
  언급한다. 기준은 "노래가 없어도 들을 만한가". LLM 원창작 에세이·유머는 밋밋해 유명한 이야기 다시 들려주기로. 결론은
  인문학적으로 확실히 맺되 이야기가 벌어놓은 만큼만.
- **"노래 틀어줘" 는 그대로 노래**: 이야기는 별도 요청("이야기 해줘")으로만 진입. 되묻지 않고 바로 시작.


## 1차 — 이야기용 백엔드로 교체 (2026-09-28)

- **대본은 백엔드가 통째로 든다 (파이썬 커서 없음)**: live instructions 는 세션 후 append 3종·각 500 토큰뿐이라 대본이
  안 들어가고, 백엔드(responses)는 `session.update` 로 통째 교체 가능. (→ 이후 2차에서 대본을 `thinking.append` 로 대화
  모델에 직접 넣는 방식으로 대체)
  - 처음엔 단락마다 `next_part` 툴로 넘기려 했으나, 백엔드가 매 위임에 대화 이력 전체를 받으므로 대본 전문을 주고
    "이력에서 진행 위치를 읽어 다음 단락을 돌려줘" 로 단순화 — 단락마다 툴 왕복(~2 초)이 빠지고, 곁길 질문("그 왕자
    이름이?")도 대본으로 답한다.
  - 대가는 진행 위치 오판(반복·건너뜀) 가능성. 실기에서 잦으면 커서 툴을 다시 넣는다.
  - 대화 모델이 단락을 자기 말로 옮기므로 사실 통제는 백엔드가 원문을 돌려주는 데 있다.
- **파싱은 frontmatter 만**: 고를 때는 요약·태그·곡만 보고, 정해진 뒤엔 본문(곡 프로필 + 단락 + `>` 지침)을 그대로
  지시문에 넣는다. 단락 구조를 파이썬이 알 이유가 없어 `Part` 같은 구조체를 두지 않았다.
- **검색 → 선택 → 시작을 고정 시퀀스로**: 후보를 백엔드 지시문에 상시 넣지 않고 `search_stories(query)` 로 받게 했다.
  지금은 키워드 점수 + 무작위 채움이라 검색이 거의 형식적이지만, 선제 진입("대화 분위기에 맞는 이야기 꺼내기")과 이야기
  수 확장 때 검색 안만 바꾸면 되도록(임베딩은 `IEmbedder` 재사용 가능) 자리를 잡아둔 것. `start_story` 는 직전 검색
  결과의 id 만 받아 검색을 건너뛰는 진입과 지어낸 id 를 막는다.
- **한 이야기 제외는 기계적으로**: `story_plays` 테이블(ray.db)에 시작 시점을 기록하고 검색이 그 키를 후보에서 뺀다.
  프롬프트로 "이건 하지 마" 가 아니라 백엔드가 존재 자체를 못 보게. 전부 한 바퀴 돌면 오래된 순으로 다시. 같은 세션 두
  번째 이야기도 검색이 DB 를 다시 보므로 백엔드 설정 갱신이 필요 없다.
- **단락 1 은 툴 결과로 준다 — 같은 위임의 후속 응답에는 백엔드 교체가 반영되지 않았다 (실기 2026-09-28)**:
  - 처음엔 `update_backend` → 결과 제출 순서면 후속 응답(단락 1)을 이야기용 백엔드가 만들 거라 봤는데, 10 ms 뒤의
    이어가기가 기본 백엔드 말투("좋아, 이야기 들려줄게" 한 줄)로 답했고 대화 모델은 내용 없이 이야기를 지어냈다.
  - 어댑터 문서의 "이후 위임부터 적용" 이 맞는 것으로 보인다(비동기 지연인지 위임 단위 고정인지는 미구분). 노래는 후속
    답이 어느 쪽이든 빈 답이라 드러나지 않았던 것.
  - 그래서 `start_story` 결과에 `first_part`(단락 1 텍스트, `>` 지침 제외)를 실어 기본 백엔드가 그대로 답하게 하고, 단락
    2 부터는 새 위임이라 이야기용 백엔드가 맡는다. `finish_story` 는 복원 뒤 결과 제출(후속 답은 기본 백엔드).
- **이야기 지시 append 는 출력 무음 뒤에, 그리고 start_story 결과는 그 뒤에**: `instructions.append` 는 진행 중 발화를
  끊는다(어댑터 문서).
  - 1차 구현은 `start_story` 처리에서 바로 보내 위임 시 한마디("어떤 이야기로 해…")가 잘렸다.
  - 2차(결과는 즉시 제출, append 만 무음 대기)는 단락 1 이 곧바로 시작돼 10 초 뒤 문장 사이 쉼(0.5 s)에 append 가 떨어져
    이야기 중간이 끊겼다 — 긴 낭독 중엔 안전한 틈이 없다.
  - 그래서 노래 PENDING 처럼 **결과 자체를 보류**한다: 한마디가 끝나 무음 0.5 s → append → 결과 제출 → 이어가기. 단락
    1 은 append 뒤에야 도착하므로 append 시점엔 반드시 조용하다.
  - 대안(이야기 규칙을 세션 시작 지시문에 조건부로 상시 포함)은 타이밍 문제가 없지만 이야기 중에만 규칙이 있는 쪽을
    택했다.
- **노래로 끝나면 노래 흐름이 이어받는다**: 이야기용 백엔드가 `play_song` 을 부르면 이야기 상태를 지우고 노래용
  백엔드로 교체, 노래 끝의 기존 복원이 기본으로 돌린다. 노래가 시작 전에 취소돼도 이야기로 돌아가지 않는다(단순화).


## 2차 — 백엔드 교체 폐지, 종료 판단은 백엔드가 전사로 (2026-09-29 ~ 10-01)

대본을 `thinking.append` 로 대화 모델에 통째로 넣는 방식이 안정되자 이야기용 백엔드(별도 지시문 + 대본 전문 + 툴 집합
교체)가 하던 일이 거의 사라졌다. 남은 건 "제안 곡 id 가 뭔지" 와 "지금 이야기 중인지" 두 사실뿐이라 `## Current story`
절 한 개만 붙여 `session.update` 하고 툴 집합은 세션 시작 그대로 둔다.

- **왜 교체를 없앴나**: `session.update` 는 *다음* 위임부터 적용되므로 `start_story` 를 부른 위임은 여전히 이전 설정으로
  돈다. 그래서 "start_story 뒤 빈 응답" 규칙을 기본 백엔드에도 넣어 우회하고 있었다. 지시문이 하나면 이 경합 자체가
  없다. 대본 전문을 백엔드에 참고로 주던 것도 대화 모델이 이미 대본을 갖고 있고 "available answers 는 위임하지 말라" 고
  돼 있어 쓰일 일이 없었다.
- **툴 3개(`search_stories`/`start_story`/`finish_story`)는 항상 노출, `change_story` 는 없앴다**: 교체는 `finish_story` +
  `search_stories` 를 한 응답에, 다음 응답에 `start_story` — 백엔드가 이미 아는 "끝났으면 `finish_story` 먼저" 와 같은
  꼴이다.
  - 상태 가드는 루프에 있다(이야기 중이거나 전송 중 `start_story` → "call finish_story first", 이야기 없을 때
    `finish_story` → `not_telling`).
  - 이야기 중 `start_story` 를 교체로 받지 않는 이유 — 백엔드가 이어가기용으로 `start_story` 를 헛 부르는 사례가
    있었고, 그게 이야기를 갈아엎으면 안 된다.
  - 대가는 교체 사이에 대화 모델이 `STORY_ENDED` 를 한 번 받고 곧 새 준비 지시를 받는 것뿐이다.
- **`play_song` 은 스스로 이야기를 끝낸다**: 루프가 `play_song` 시점의 TELLING 여부로 "이야기에서 온 노래" 를 표시하고,
  그 플래그가 노래 자연 종료 뒤 감상 질문을 결정한다. 백엔드가 `finish_story` 를 먼저 부르면 재생은 되지만 그 플래그가
  빠지고 백엔드 복원·노래용 교체가 한 번 낭비된다. 그래서 프롬프트는 "금지" 가 아니라 "play_song 이 이야기를 끝내니
  finish_story 는 같이 부르지 않는다" 로 적었다.
- **자연 종료는 툴 호출이 아니다**: 대화 모델이 노래 제안까지 말하고 사용자가 동의(`play_song`)도 거절(`finish_story`)도
  않고 딴 얘기로 넘어가면 아무도 종료를 알리지 않아 TELLING 이 세션 끝까지 남는다 (침묵 재촉 반복, 다음 `start_story`
  오류, 이후 아무 노래에나 감상 질문).
  - 대화 모델에게 "제안 뒤 어떤 답이든 위임" 을 시키지 않기로 했다 — 위임은 확실한 경우(노래 거절·중단·재개 거절)에만
    기대한다.
  - 대신 백엔드가 받는 입력이 대화 이력 전체([FINDINGS §4](../../scripts/gpt_live/FINDINGS.md))라는 점을 써서, 이야기 중
    어떤 이유의 위임이든 먼저 전사를 보고 제안이 이미 나왔고 사용자가 넘어갔으면 `finish_story` 를 *먼저* 부르게 했다.
    한 응답의 호출은 루프가 순서대로 넘기므로 `finish_story` → `search_stories` 가 같은 응답에 와도 다음 `start_story` 가
    통과한다.
  - 출력 전사에서 곡 제목을 찾는 루프 쪽 휴리스틱은 대화 모델이 바꿔 말하기 때문에 보류. 백엔드 판단이 실기에서
    흔들리면 그때 안전망으로 추가.
- **지시문·툴 설명 분리(OpenAI function-calling 가이드)**: 툴 설명은 "무엇을 하는지 + 인자·결과 형식" 만, "언제
  부를지/부르지 말지" 는 백엔드 지시문의 Task instructions 에만 둔다. 전에는 `set_brightness`, `search_stories` 설명에
  대화 정책이 들어가 프롬프트와 이중 관리였다. Task instructions 는 Information / Device / Music / Stories / Ending 블록으로
  묶었다. [decisions-wip.md 의 차후 고려](../decisions-wip.md#차후-고려) 에 있던 조명 상태 질문 구멍은 이 정리에서
  문구를 넣었지만(`get_device_settings` 없이 상태를 말하지 말 것, `off` = 꺼짐) 실기 미검증.


## 기록 당시 남은 문제

1차 설계의 실기 검증 전 (미확인) 항목:

- (a) 백엔드의 검색→시작 연쇄 툴 호출 성공률 — 검색 결과를 말로 설명해 버릴 위험
- (b) 대화 모델이 300 자 단락을 요약하지 않고 다 말하는지
- (c) 질문 단락에서 멈추고 답을 받은 뒤 위임하는지
- (d) 곁길 후 복귀 시 진행 위치
- (e) 위임 중 "잠시만" 류 군소리

`scripts/gpt_live` 하네스로 재고 프롬프트를 깎을 계획이었다. 대본 생성 프로세스(곡 프로필 검색 → 이야기 후보 → 대본,
사람 검토 사이에)와 선제 진입은 다음 단계로 미뤄 두었다.
